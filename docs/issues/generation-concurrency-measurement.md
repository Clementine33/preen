## 测量环境和口径

- 实际只读 CIFS / SMB 3.1.1 媒体挂载，本地 NVMe / Btrfs 数据库副本；TMPDIR 放在工作树 `.dev_data/concurrency-tuning/tmp`，没有使用 `/tmp` 的 tmpfs 存放数据库。
- 输入为 2026-10-14 的静态开发库备份，74 个可读成员目录，备份含 23,094 个文件、1,510 个音频条目。大量缺失场景只清空副本的 bitrate，单会话实际补测 1,473 个文件。
- 备份的生成、库存主表与当前一致；缺少新版合集表、个人数据表含旧列。本轮不读写这些表，不声称该备份是完整当前 schema。
- NAS 物理盘型未现场核验；历史原始记录为 HDD。没有清宿主机缓存或验证磁盘电源状态，因此以下均为预热后的自然缓存 / 热缓存结果，不是受控冷测。
- 每个正式系列为 5 对基线 / 候选，顺序 AB / BA 交替。测量期间不并行运行测试、lint 或其他候选负载；不删除异常样本，不追加轮次改变门槛。
- `Latency[i]` 是从整批入队前起算的第 i 个请求完成时间，含入队与最多约 5 ms 轮询误差；不是纯执行耗时。`Queue` 只计 dispatcher claim 前等待，不含新扫描槽等待。
- 阶段 `Work` 是各次调用累计耗时，可能重叠，也可能包含等待和背压，不能相加当作端到端耗时。RSS / CPU 是整个测试进程及子进程口径，不是某一阶段独占资源。

## 已定位的限制

事实齐全的单会话样本：总耗时约 2.77 秒，输入刷新约 2.66 秒，其中 merge 约 1.77 秒；实际计划分析约 0.095 秒，快照持久化约 0.007 秒。该负载主要受扫描与合并影响，提高计划会话数不会加快这一个请求。

事实缺失时，媒体探测成为另一条主要路径。最初未预热样本耗时 33.19 秒，预热后基线中位数约 5.98 秒；前者仅保留为预热观察，不与后续候选比较收益。

历史原始扫描记录补充了 ADR 汇总没有保留的区分：NAS 本地 HDD 的 16→32 作品 worker 有约 14.70% 的两次纯扫描均值收益，同时设备请求平均时间约 19–20→32–33 ms；SMB 早期单组冷 / 热收益仅 1.66% / 5.40%。它们不是同一环境或同一计时范围，不能合并为“32 对所有机械盘最优”。

原始历史入口位于原仓库 `.dev_data/scan-benchmarks/2026-10-03/README.md`；当前可追踪的摘要见 [历史性能记录](adr-performance-evidence.md)。

## 本轮实现

1. 保留计划会话默认 2、扫描宽度 32、单计划作品分析 4、每作品探测 4；后台探测默认 8 与编码池不变。
2. 同一个转换 Task 的输入刷新共享一个扫描槽。不同会话的 selected scan 不再叠到 64；压力测试的实际 walk 峰值由 64 降至 32。分析阶段仍可与其他会话重叠。
3. 等待扫描时每 100 ms 调用既有取消检查，支持持久化取消标志；取消、失败和完成均释放槽位。
4. 手动测量入口不增加产品配置项。内部宽度候选通过 Go source overlay 比较，避免把实验开关留给用户。
5. 选中范围的覆盖校验改为一次构造索引范围结果；过期条目清理按 staging 主键逐项查询，避免每个 scope 重建完整路径列表。原有根路径、边界、会话检查及事务回滚保留；增加多个范围、相邻前缀、错误 root、scope marker 的拒绝与原子性测试。
6. 文件级 `auto_vacuum` 不再在每条连接初始化时重复设置。只在空库创建前设置并持久化增量模式；现有库不执行 VACUUM 或模式转换，外键、WAL、busy timeout 和 immediate 写事务规则不变。

## 第二阶段：数据库瓶颈与稳定性诊断

额外真实负载 race 验证暴露了两层问题，原始调度基线也失败，不能归为扫描槽回归：

- 修正前读取生成状态报 `SQLITE_BUSY`；最小回归在持有一个写事务时创建新连接执行只读查询，旧实现约 0.5 秒内无法完成，释放写事务后才返回。
- 保持 WAL 和文件增量回收模式相同，逐项移除连接参数：仅移除 `auto_vacuum` 可令最小回归通过，移除 WAL 设置或 immediate 策略均仍阻塞。该文件级设置不应要求每个新读连接重新取得写锁。
- 移动初始化后，大负载 race 仍出现长事务下的写超时和终态写失败，原来的全量 scope 校验及重复构造 staging 路径集合是继续缩短合并时间的目标，不能只放大 busy timeout 掩盖。
- 预筛中，仅优化覆盖集合时 merge 约 1.45 秒；再将过期清理改为主键查询后约 0.215 秒。正式最终对照中 merge 中位数为 0.237 秒；此前失败的真实混合负载 race 复现最终通过（约 28 秒），不是靠增加超时或吞掉错误通过。

没有采用“所有内部并发一律降低”。一个额外的共享探测预算 16 预筛样本没有显示端到端收益，未落地，也不宣称已排除它在其他负载上的价值。

## 会话默认 2 的结论边界

已有测量不能证明 2 最优。本轮消除了会话数直接放大扫描并发的问题，暂保留默认值。

混合任务的一轮探索中，候选实现下会话数 1 / 2 / 4 的重命名完成时间约 5.94 / 3.31 / 0.36 秒，元数据约 6.07 / 3.48 / 0.23 秒，说明更多会话可能改善轻量任务排队。这不是充分验收：缺失事实下更多会话仍可能叠加探测，冷缓存和多个独立库尚未对照，因此本轮不直接把默认改为 4。

扫描槽目前跨所有转换会话共享，不按物理设备区分。独立多磁盘的并行扫描吞吐可能下降，须在这种负载出现时单独验证；本轮不引入设备识别或新的调度层。

## 复现入口

从 `backend/go` 执行，TMPDIR 指向实际磁盘目录，输入必须是没有 WAL 的静态备份：

```sh
CONCURRENCY_MEASURE_DB=/absolute/path/to/backup.db \
CONCURRENCY_MEASURE_WORKSETS=workset-id \
CONCURRENCY_MEASURE_ROUNDS=5 \
CONCURRENCY_MEASURE_SESSIONS=2 \
CONCURRENCY_MEASURE_SCAN=32 \
CONCURRENCY_MEASURE_OUTPUT=/absolute/path/to/results.json \
TMPDIR=/absolute/path/on/nvme/tmp \
go test ./internal/conversion -run '^TestMeasureGenerationConcurrency$' -count=1 -v
```

- 大量缺失：增加 `CONCURRENCY_MEASURE_MISSING=1`，只修改副本。
- 共享磁盘压力：增加 `CONCURRENCY_MEASURE_COPIES=4`。
- 实际轻量任务：增加 `CONCURRENCY_MEASURE_LIGHT=1`；输入备份须包含该工作集的重命名与元数据操作草稿。
- 内部宽度和基线对照：用 `go test -overlay=/absolute/path/to/overlay.json -c` 分别构建测试二进制，再交替运行。第一阶段基线只去掉 Task.New 的扫描槽接线，其余实现相同；最终组合对照基线保留原 SQL 与原连接参数，不能用只去掉扫描槽的版本替代。
