# 0010 部署级公共设置

Date: 2026-09-25

Status: Accepted

转换的五项公共设置（`mode`、`delete_mode`、`classifier_tags`、`matched`、`unmatched`）过去只活在某一个处理记录的草稿里。「转换全局设置」页面读的其实是当前记录的草稿，于是同一台机器上的两个媒体库可以长期持有两套不同的公共设置：用户在第一库改完设置，进第二库看到的是旧值，还会以为自己的修改丢了。0006 §3 已经明确否认「草稿里的活引用」（策略槽与标签库都是复制），所以不能反过来让草稿引用某个模板；这里需要的是一个明确的推（push）语义：公共设置全部署一份，任何一处保存都同步到所有记录。

## 1 一份存储，作为新记录的起点

- `common_settings` 表按 `operation_type` 隔离载荷；本次只有转换 Task 写入。公共载荷不另存 `schema_version`：它由已校验的草稿投影而来，全局同步仍逐条检查草稿自身的版本。未接入的 Task 没有全局设置行，无需提前聚合它们的设置。
- 草稿 JSON 与 `workset_operation_drafts` 行里的 `schema_version` 表示同一个 Task 草稿格式；后者供通用层转发载荷版本，不是另一套设置版本。
- 新建处理记录时，服务读出该载荷，交给 Task 作为种子草稿的起点；没有存过、或载荷任务读不了时，用任务自己的种子值（不因为一条坏数据拒绝创建记录）。
- 没有全局值时，**替换记录沿用被替换记录自己的公共设置**；另一个记录最近保存的可能只是成员覆盖，不能据此推断公共偏好。其他库的新记录仍用任务种子值，直到用户从所选记录明确应用全局设置（§2）。
- 本次建表使用 `CREATE TABLE IF NOT EXISTS`，不改变现有数据库的 `schema_meta` 标记；跨标记的数据库升级与兼容不在此决策范围。
- 记录创建先读载荷再写自己的记录，与一次全局保存并发时最坏结果是这条记录停留在上一版公共设置；下一次从任何一处保存都会把它收敛回来，不值得为它引入跨写事务的读。

## 2 沿用草稿保存接口，一次事务推给所有记录

- 公共字段发生变化时自动全局保存；设置页也可在值未变化时显式提交 `apply_common_settings:true`，使旧数据库里选定记录的既有公共值首次成为全局值。只改成员覆盖且未显式应用时，仍只写当前记录。
- 设置页从草稿读取结果判断公共值是否已经与部署级载荷一致；无部署级值或两者不同时允许应用，避免把页面内临时的“点过应用”当成持久状态。
- 全局应用时，同一事务内写入：当前记录的新草稿（含本次成员编辑）、部署级载荷，以及该 kind 下每一条仍可编辑记录的新草稿——公共字段整体替换，成员记录（覆盖、排除、以及"没有覆盖"这件事）逐字保留，草稿哈希与 operation 版本一并推进。
- 候选集合与每条候选的会话状态都在该事务内重新读取：任何一条待同步记录正在生成或执行，整次保存以冲突拒绝，不留部分更新。孤立的记录（库已不存在）只读，永不参与同步（0001 §5）。
- 拒绝是整体的，所以「读不出草稿」也必须拒绝：某条记录的草稿任务读不出来（缺行、被改坏、未知的草稿 schema 版本），就整次保存失败，绝不跳过它——跳过正是这条规则要消灭的部分更新（0004 §5：宁可拒绝也不猜测）。
- 首次保存以当前记录的公共设置覆盖其他记录：这是全局值"从哪开始"的确定选择，也让升级前创建的记录在第一次保存时被拉到同一版本。
- 拒绝只把冲突留给"当前记录忙"：别的记录忙时返回独立的 `COMMON_SETTINGS_BUSY`，界面才能说出「是另一个任务在跑」，而不是让用户以为自己这个页面的操作有问题；读不出草稿则返回 `COMMON_SETTINGS_UNREADABLE`，指出要重建哪条记录。

## 3 计划不被改写，只是过期

全局保存只动草稿。已生成计划是冻结快照，原样保留：同步后的记录读作 `needs_planning`，执行前必须重新生成——这是 0006 §2 既有的推导（草稿哈希 ≠ 冻结哈希），本案不新增第二条判定，也不让同步去改写任何 revision 行。

## 替代方案权衡

- 拒绝「公共设置做活引用」（草稿引用一个模板行）：与 0006 §3 冲突，模板一改，历史计划与已保存草稿的含义都会变。
- 拒绝把公共设置拆成独立的运行时表供读取时合成：草稿必须是自洽快照，且 `needs_planning` 的推导基于整份文档的哈希；拆开会让「这条记录现在的设置」与「这份草稿」两个事实分叉。
- 拒绝逐记录串行写入（写了 A 再写 B，中途失败就停）：用户会看到一半记录新、一半旧；也拒绝用后台任务补偿，同步是按下按钮的直接后果，必须整体成功或整体拒绝。
- 拒绝在忙碌时跳过忙碌记录：那正是部分更新，确定性的拒绝比静默的不一致好；读不出草稿的记录同理。
- 拒绝为新记录单独维护一套「新草稿默认值」：起点就是这份存储，否则每个新记录都得重放用户上一次的选择。
- 拒绝用「最后保存过的草稿」猜测全局值：成员编辑也会刷新保存时间，可能把未修改的默认公共值误选为全局值。
- 拒绝按数据状态切换提示文案（"仅影响本任务"）：公共设置就是全局的，文案不该随状态变化。
