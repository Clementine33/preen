# 0008 部署级公共设置

## 背景

转换的公共设置起初只保存在某一个处理记录的草稿里，「转换全局设置」页读的其实是当前记录的草稿。同一台机器上的两个媒体库因此可以长期持有两套公共设置：用户在第一个库改完，进第二个库看到的仍是旧值，以为修改丢了。草稿和计划保存配置快照，因此公共设置需要显式推送。

部署级载荷落地后又暴露出第二个问题：它只能经某条记录的草稿读写，没有记录的库根本看不到自己的设置，转换、重命名与元数据刷新三处设置界面也各存各的。

## 决定

1. **部署级单一权威事实（Deployment-wide Common Settings）**：
   - 不再提供独立的命名策略模板；转换配置统一经公共设置和成员覆盖编辑。
   - 公共设置按 Task 类型隔离，每类一份部署级载荷；转换、重命名、元数据刷新三种 Task 共用同一套机制。它独立于任何处理记录而存在，没有记录的库也能读写。
   - 新建的处理记录以该载荷为种子草稿的起点；没有存过或载荷读不了时，用 Task 自己的种子值。
2. **唯一写入口 `GET/PUT /api/v1/tasks/{type}/settings`**：
   - GET 返回已存载荷，没存过则返回 Task 的种子值。PUT 是公共设置的唯一写路径；草稿 PUT 不再改动它们。
   - 并发令牌是已存载荷的规范化 JSON 哈希（`ETag`），PUT 必须带 `If-Match`；无需改 schema。尚未存过时，令牌是种子值的哈希。
   - 路径以 Task 命名，避免与日后的应用级设置页（`/api/v1/settings`）混淆。
3. **显式事务性全量推送**：
   - PUT 在单个数据库事务内原子更新全局公共记录，并全量推送到该 Task 类型的所有现存可编辑草稿中。
   - 推送时整体替换各草稿的公共段，成员记录（覆盖、排除以及「没有覆盖」这件事）逐字保留；每条草稿的哈希与 operation 版本随之推进。
4. **严格的全有或全无守卫（All-or-Nothing）**：
   - 候选集合与每条候选的会话状态在事务内重新读取：任一待同步记录正在生成或执行，或其草稿缺失、损坏、schema 版本未知，整次保存以冲突拒绝（`COMMON_SETTINGS_BUSY` / `COMMON_SETTINGS_UNREADABLE`）。跳过它正是这条规则要消灭的部分更新。孤立记录（库已不存在）只读，不参与同步。
5. **草稿 PUT 不碰公共段**：
   - 提交的公共段与部署级载荷不同，以 409 `COMMON_SETTINGS_MISMATCH` 拒绝，既不应用也不忽略；从未存过载荷时，参照记录自己已存的公共段，成员级编辑不受影响。
6. **冻结计划免疫**：
   - 公共设置的保存与推送仅作用于未执行的草稿，不改写已经生成的冻结计划。草稿哈希变动后，既有的计划新鲜度校验机制自然识别并提示用户重新生成。

## 放弃的方案

- **逐记录异步后台补偿同步**：会暴露漫长的中间不一致状态，且后台静默重试机制复杂。
- **运行时动态合成全局值（不物理写进草稿）**：导致草稿与其生成的计划无法形成确定性快照，草稿哈希校验随之失效。
- **由界面在前端并发发起多个媒体库的更新请求**：网络抖动或部分失败会留下难以排查的脏配置。
- **经草稿 PUT 写公共设置（公共段有变化即全局保存，另加 `apply_common_settings` 标志与 `common_settings_current` 回显）**：没有记录就无法读写；「这次保存算不算全局」取决于与该记录旧草稿的比较，同一个请求体的含义随记录而变；界面还得靠回显字段猜自己与全局是否一致。
- **用 operation 版本做设置的并发令牌**：载荷是部署级的，没有哪条记录的版本能代表它；另建版本列要改 schema，而规范化哈希已经足够。

## 后果

- 同类记录中任一条正在生成或执行时，公共设置无法保存，需等该会话结束。
- 设置界面只需读写这一个端点，有无记录都一样；每条草稿的公共段始终等于该载荷（尚未存过时除外）。
