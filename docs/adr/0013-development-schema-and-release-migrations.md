# 开发 schema 自由迭代，发布库通过 goose 升级

## 1 两种数据库生命周期

本决策将数据库分为开发和发布两种生命周期：开发模式以 `schema.sql` 描述最终结构，只在空库初始化，不自动补表；发布模式执行嵌入的 goose SQL 迁移，新库从完整历史创建，已有库按顺序升级。开发迭代中的中间结构无需成为永久迁移历史，而已分发数据库仍有可重复的升级路径。

选择用 `schema_meta.database_mode` 区分开发库和发布库，二者不相互转换。首个发布迁移建立新基线，不接管原有 v4 和无迁移历史的数据库；高于程序支持的迁移版本也拒绝打开，以免把未知结构当作可升级基线。此决定替代 ADR 0008 §3 对数据库升级的全面拒绝，其留存、回收及连接/事务决定继续适用。

## 2 只有发布边界冻结迁移

版本选择采用 `X.Y.Z-dev` 对应开发模式，发布版和对外 RC 对应 goose。RC 已经可能产生需要后续升级的用户数据库，因此与正式发布采用同一生命周期；构建元数据不影响模式，程序版本也不充当迁移编号。

迁移历史的冻结点选在首次分发：此前只保留发布之间的最终结构差异；此后以追加迁移表达修正。若重写已经分发的文件名、编号或内容，同一版本号可能代表不同结构，升级结果便取决于用户安装过哪个构建。

## 3 升级前备份，失败阻止启动

选择在已有发布库执行待运行迁移前，用 `VACUUM INTO` 保存含已提交 WAL 内容的一致性备份，验证后再迁移。直接复制主数据库文件可能漏掉 WAL 中的提交，因此不足以提供恢复基线。

备份或迁移失败阻止启动，以免业务运行在未知结构上；已经成功的迁移在重试时跳过。升级只支持 Up，恢复采用备份与对应旧程序，不依赖可能丢失数据的 Down。备份不自动清理，以免删除用户仍可能需要的恢复点。

## 拒绝的替代方案

保留手写 SQL，不引入 GORM；开发中间步骤不成为永久迁移历史。独立开发、本地单实例使用现有测试与发布后不可变约定，不增加发布清单、摘要校验、进程锁或额外流水线。
