# SQLite 写竞争测量

日期：2026-10-11。基线：`b70dca6` 加本次关停修复；Linux/amd64、Go 1.27.1、modernc SQLite 1.59.0。

## 范围与口径

使用实际服务装配和业务准入门，仅运行允许重叠的工作。七种场景各运行五次，共 35 次；每次同时通过 HTTP 修改作品个人数据，累计 10,819 次编辑。夹具含 2,000 个作品、2,128 个副本、27,664 条库存项；重命名与元数据刷新各选 128 个成员，转换规划选 500 个成员、6,000 个音频文件。

网络和媒体探测使用模拟依赖，分别延迟 20 ms 和 2 ms；源请求保留 100 ms 启动间隔。数据库、事务、扫描、规划和目录重命名走实际实现。此结果只描述该合成负载，不代表生产硬件的容量或延迟上界。

BEGIN 耗时含获取 SQLite 写锁的等待；事务持锁耗时从 BEGIN 成功后计至 COMMIT/ROLLBACK。下表取五次运行的最大值；p99 仅纳入**同一路径、单次运行至少 100 个 BEGIN 样本**的统计，不合并稀疏路径凑样本。

## 结果

| 场景（均叠加 HTTP 编辑） | 最大 BEGIN 耗时 / ms | 最大合格 p99 / ms | 最大事务持锁 / ms |
| --- | ---: | ---: | ---: |
| 全库扫描与合并 | 429.12 | 样本不足 | 154.41 |
| 元数据规划、刷新与封面 | 18.51 | 8.38 | 14.31 |
| 媒体事实、元数据与封面 | 178.72 | 8.38 | 123.60 |
| 目录重命名 | 103.54 | 0.07 | 6.67 |
| 留存清理、增量 vacuum 与 checkpoint | 8.46 | 样本不足 | 0.95 |
| 跨库扫描与元数据会话 | 429.05 | 8.53 | 144.17 |
| 转换规划 | 1,729.83 | 1.13 | 1,542.30 |

35 次真实准入负载中，所有 SQL 尝试均未出现 BUSY/LOCKED，全部 HTTP 编辑成功。共享连接池未设置连接数上限，连接池等待次数与等待时间均为零；这不等于没有 SQLite 锁等待。

转换规划的 1.73 秒 BEGIN 耗时和 1.54 秒事务持锁值得关注，但对应路径样本不足，不能把最大值称作 p99。

独立的强制竞争测试中，12 个并发调用方完成 1,200 次存储调用，零失败、零 BUSY。另一连接持写锁 200 ms 时，应用写入等待约 230 ms 后成功；持锁 5,500 ms 时，应用在约 5,007 ms 返回 SQLITE_BUSY。后者属于外部竞争，进程内单写入口无法消除。

## 结论

**在该规模下未复现需要全局单写入口的问题。** 没有进程内 BUSY，合格 p99 均低于 9 ms，未达到预设的 2.5 秒评估阈值。强制竞争结果不用于论证改造必要性；本次也没有单写入口或批量提交的 A/B 对照，不能据此声称吞吐收益。

当前暂不改造的决策及重新评估条件见 [ADR 0023](../adr/0023-defer-single-writer.md)。
