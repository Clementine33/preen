# 0007 业务分包与依赖方向

## 背景

旧后端代码按技术机制进行横向分层（如 `repo`、`httpapi`、`usecase`、`services`）。HTTP 控制器直接持有底层具体的数据库 Repository，具体的转换任务又直接在 SQLite 实现内部读写库存。一个核心业务概念的改动往往需要跨越 4-5 个不同机制目录，层名未能表达实际的业务聚合边界。

## 决定

1. **按业务聚合垂直分包**：
   - 核心领域概念划分为独立的业务包（如 `library`、`workset`、`conversion`、`inventory`、`works` 等），业务状态、类型校验与核心生命周期在同一个包内自治。
   - 外部驱动（HTTP 路由、SSE 处理）与物理设施（SQLite、文件系统、外部 ffmpeg 进程）统一放置在 `internal/adapters` 适配器层。
   - 装配与依赖注入在 `internal/app` 完成，`cmd` 仅负责启动引导。
2. **消费者窄端口（Consumer Ports）与单向依赖**：
   - 业务包不依赖具体的适配器实现或 `app` 装配包；依赖方向严格由外部指向业务。
   - 接口端口由消费方根据自身所需的操作进行最小化声明，避免为了通用性在仓储层暴露宽大笨重的公用 Interface。
3. **架构守卫自动化检查（`internal/arch`）**：
   - 将包分层规范固化为自动化单元测试，静态分析包导入图，对具体的禁止边做断言（业务不导入适配器与装配层等）；包之间的循环由 Go 编译期拒绝。纯核心（`librarypath`、`conversion/reconcile`）不引入任何网络、文件系统与数据库依赖。
4. **事务不变式优先于表粒度抽象**：
   - 保持原子存储操作的内聚，不为了追求“单表对应单 Repository”的纯粹性，而把批次替换、计划发布等必须在单事务内完成的操作拆散为多次独立的无事务读写。

## 放弃的方案

- **经典三层/四层水平技术分包**：一个业务概念的改动要跨越多个机制目录，层名表达不了业务边界。
- **由实现方预先定义通用大接口**：服务提供方难以预估所有消费方的真实需要，容易导致方法泛滥或产生过宽的 Mock 对象。
- **在包迁移期保留中间全局别名**：容易掩盖真实的循环依赖，使得重构半途而废。

## 后果

- 新增业务特性时，开发者可以主要聚焦于特定业务包及其专用端口。
