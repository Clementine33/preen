# 0006 执行会话、编码池、只读校验与安全发布

## 背景

音频转码是典型的高 CPU 与高 I/O 混合型重任务。逐文件串行执行 ffmpeg 无法有效利用多核算力；无界并行则让暂存文件与失败时丢弃的工作失去上限。执行前全量重扫媒体库代价高，失败后自动回滚又可能在未知磁盘状态上再次写入。

## 决定

1. **会话内跨成员共享有界编码池**：
   - 会话级别保持全局串行，会话内部跨选定成员共享固定大小的有界 Worker 编码池。
   - 组件准备窗口与 Worker 数保持一致，未提交的组件持续占槽，限定暂存文件规模与预检的陈旧程度。
2. **轻量只读新鲜度校验**：
   - 执行阶段不再启动重型库存扫描，仅对实际待执行的音频单元进行只读快速遍历，对比数量、相对路径、文件大小与整数秒 mtime。
   - 校验通过直接开始处理；若输入事实漂移则拒绝执行并尽力刷新受影响库存。
3. **安全单向发布与严格移动（Strict Move）**：
   - 暂存文件存放在目标同级，单任务独占。编码完成后关闭写句柄，只读重开校验其大小、类型与媒体事实，再按冻结顺序提交。
   - 跨平台采用严格无覆盖移动机制（Linux 优先原子改名，回退硬链接；Windows 采用原生无覆盖移动），挂载点跨越无法保证时直接拒绝。
4. **单协调者顺序提交与逐组件持久化**：
   - 单一协调者按冻结顺序提交文件系统操作、移除过时音频并持久化结果。
   - 每个组件的结果与会话进度在独立的短事务内写入数据库，不在事务内执行编码与磁盘 I/O。会话行不设整份报告列：在每个组件边界重写整份报告会让写入量按 O(N²) 增长。事件流轮询只读控制信息投影，明细由冻结清单与已记录结果装配。
5. **首错即停与部分成功权威性**：
   - 首次遇到不可恢复的真实 I/O 错误即停止后续未执行组件，等待所有在途 Worker 退出后安全收尾。
   - 已经提交的组件不自动回滚；组件内的部分改动如实记录在结果信封中，不伪报为未运行。

## 放弃的方案

- **无界准备窗口**：窗口限定的是预检在编码前能有多旧、同时存在的暂存规模，以及一次失败会丢弃多少工作。慢的头组件占槽导致 worker 闲置，是选择简单窗口 W = N 的代价。
- **每个成员文件夹一个池或按文件夹分批**：成员文件夹不是工作负载的自然边界，池与窗口应当跨它们流动。
- **全会话原子回滚**：当硬件崩溃或断电发生时，自动撤销已落盘的文件很脆弱，在未知磁盘状态上二次写入甚至可能抹除用户的原始资产。保留明确的部分成功事实，交给用户检查并生成新计划更为安全。
- **Opus 输出逐文件完整解码**：Opus 改用 Go 的单逻辑流 Ogg 检查（逐页 CRC、顺序、完整 packet 与 EOS），同一遍读取计算 SHA，并保留 ffprobe；五组交替实测通过预设门槛后采用。MP3 与 M4A 仍保留完整解码，不增加各自的容器解析器。

## 后果

- 遇到环境故障时可能留下部分成功的组件，用户需要根据返回的权威明细在下一轮规划中收敛。
