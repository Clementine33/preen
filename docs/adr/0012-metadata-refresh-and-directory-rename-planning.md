# 0012 元数据刷新、目录重命名与修复、封面投递

实施状态：2026-10-23 祖先补抓已接入独立关系报告写入入口，只沿存储后的有效父链补报告，失败保留证据，原作社团页面仅临时读取。

## 背景

作品不仅需要整理内部音频，还需要统一重命名物理目录规范、从外部数据源抓取元数据（DLsite、ASMR.one），并将高清主封面持久化写入本地作品目录。这些操作横跨外部网络 I/O、磁盘改名与数据库事务；需要避免网络延迟阻塞磁盘准入、进程崩溃留下改到一半的目录，以及抓取范围失控。

## 决定

1. **元数据抓取受控与显式边界**：
   - 抓取仅由用户显式触发，不与后台扫描或系统启动隐式绑定；仅针对明确指定的现有作品进行，只沿有效父版本链向上补抓，不因原作编号单独补抓关系报告，不猜父号、不扩展兄弟译作或整个家族。
   - 未收录祖先补抓用于取得必要的独立关系报告，不创建作品条目、不持久化其完整基础资料或销量、不触发封面下载。为目标作品提取原作社团等信息可以临时读取原作页面，但临时读取不等于把原作完整收录。
   - 报告独立保存来源与抓取时间，作品删除或重新收录不重置仍存续报告的新鲜度；普通作品来源状态不再重复充当关系报告的更新权威。
   - 网络请求位于数据库事务外，每次接受的报告将证据、校验和受影响作品的派生更新一起提交。补抓失败保留此前有效报告，缺失信息保持未知并提示失败，不能将请求失败写成空报告或伪造跳过中间页的关系。
   - 元数据规划冻结 RJ 与路径，网络请求按 RJ 全局去重，执行时仅需轻量检查目标目录存在性，无需耗时遍历子文件。
2. **目录重命名事务迁移与启动修复**：
   - 目录重命名（`rename` Task）仅修改作品根的 basename，不自动加后缀或截断名称，冲突交给用户审阅。
   - 物理磁盘改名完成后，在单事务内原子迁移库存条目、转换凭据、副本绑定与共享成员路径，保留副本 ID 与已提取的媒体事实。
   - 系统启动阶段（在调度器与 HTTP 服务开放前）自动检查并修复中断的改名会话：若源目录已失踪但目标目录吻合，幂等完成事务性路径修复；两端都存在、都缺失或 I/O 冲突时只留诊断。
3. **独立持久化封面投递（Cover Delivery）**：
   - 元数据执行会话与封面投递解耦：封面需求持久化后，元数据会话即可结束；取消元数据也不撤销已排队的需求。
   - 封面需求归属执行；成功替换计划或删除处理记录时，旧执行与其需求一并终止。生成失败则保留旧需求；共享下载仍服务其他需求，已发布文件保留。
   - 下载使用独立客户端，只访问固定的 HTTPS CDN，逐次检查重定向、DNS 与实际连接地址，拒绝内网与保留地址，不带应用 token。下载不占准入槽，以免网络延迟阻塞扫描和写入。
   - 下载完成后，仅在发布阶段短暂申请全局准入，采用临时文件写入、校验、原子替换旧封面并清理冗余扩展名。发布过程通过 Journal 记录，确保崩溃后可重试与增量同步库存。
   - 后台维护分批回收没有任何需求引用的 `done` 下载；成功、失败或取消的投递需求都保留其共享下载，供报告和重试使用。排队及运行中的下载由 worker 或启动恢复先收尾。候选来源、已发布文件校验信息及实际文件不随下载记录回收。
   - 下载队列按普通有 rowid 表的隐式 `rowid` 领取，文本主键不决定顺序；删除中间或尾部的已完成记录后，新插入记录排在存续记录之后，状态改变不重排。这里不承诺 rowid 永不复用：最大整数分配、显式 rowid、表重建或改为无 rowid 表时须重新验证顺序，本轮不使用 `AUTOINCREMENT`。

## 放弃的方案

- **下载期间全程持有全局准入互斥槽**：网络延迟和重试会导致其他媒体库的浏览与日常文件整理长时间被锁死。
- **改名后触发全量作品重新扫描**：全量重扫会洗掉历史转换凭据、重新计算媒体属性，开销巨大；事务内原子路径迁移保留了所有关联。
- **元数据抓取自动遍历整个系列家族**：导致用户本想刷新一部作品，却意外联网抓取并写入数十部不相关的衍生作品。
- **祖先补抓复用完整作品导入**：迫使外部页面先成为占位作品才能保存关系，也会带入不需要的基础资料；外部关系报告使用独立读写路径，保留相同的来源优先级、时间判定与结构校验。

## 后果

- 封面下载与发布是异步过程：下载、逐副本发布和元数据执行分别报告结果，封面失败不改写已经提交的元数据终态。
