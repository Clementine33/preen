# 0019 出站代理：跟随系统、手动或直连

## 背景

后端访问元数据源（DLsite、api.asmr.one）与封面 CDN 时只使用设置页填写的出站代理，进程不读系统代理与 `HTTP(S)_PROXY`。前端显示远程封面则由浏览器或桌面壳的 WebView 直连 CDN，它们遵循所在系统的代理设置。于是在桌面壳里，同一台电脑上前后端走两套代理：用户只配了系统代理时，元数据抓不到而封面能显示；只配了应用代理时则相反。

## 决定

1. **出站代理分三种方式**：`system` 跟随后端所在电脑的系统代理，`manual` 使用填写的 URL，`direct` 直连。从未保存时为 `system`，这样桌面壳开箱即与 WebView 一致。`manual` 以外的方式保留已填 URL，切回即恢复。
2. **系统代理按目标逐请求解析**，因为 PAC 的答案因 URL 而异；回环目标始终直连。解析在 `adapters/sysproxy`：
   - Windows 读当前用户的 Internet 选项（WebView2 所读的同一份设置），自动检测与 PAC 由 WinHTTP 求值；求值失败时与浏览器一样回落到手动代理。
   - Linux 先看会话桌面：KDE 读 `kioslaverc`，其他桌面读 GNOME `gsettings`；没有桌面会话（容器、无头服务器）或读不到时读 `HTTP(S)_PROXY` / `NO_PROXY`。桌面设置为 PAC 或自动检测时请求失败并提示改用手动，不猜测路由。
3. **不可读的已存设置仍使请求失败**，不回落直连；系统代理读取失败同样使请求失败。

## 放弃的方案

- **后端转发远程封面**（`GET /api/v1/works/{rj}/remote-cover`，前端只从后端加载封面）：能让显示也走出站代理且跨平台一致，但远程封面挤进浏览器对后端的 HTTP/1.1 六连接池（常驻 SSE 已占一条），后端还需补缓存、并发上限与重试时长控制，按上游地址生成的 ETag 也看不到同地址上的封面更新。改动面与新增的性能路径都大于它解决的问题。
- **桌面壳给 WebView 传代理参数**（WebView2 `--proxy-server`）：只覆盖 Windows；不支持带认证的代理，改代理要重启，精确分流还需 PAC；Wails 也没有 WebKitGTK 的代理入口。
- **始终只用应用内设置、不读系统代理**：前后端在桌面壳里分裂，正是本记录要解决的问题。

## 后果

- 一个可见的设置仍决定后端如何联网；「跟随系统」被选中时，容器的环境变量才会生效。
- 浏览器访问局域网部署时，前端走浏览器所在电脑的代理，后端走服务器的设置，两者本就是不同机器，不追求一致。
- Linux 的 PAC／自动检测与 KDE「反向例外」以外的少见写法未覆盖；Windows 的 `socks=` 按 SOCKS5 拨号（浏览器视为 SOCKS4）。
