# 计划生成并发：SMB 实测与调优过程

日期：2026-10-17
结论：经过三轮实测与机制演进，计划生成并发默认值定为 **N=2**（配合固定宽度 1 的轻量规划通道）。在单库、单活跃转换计划的实际部署形态下，N=1 与 N=2 的整批耗时无显著差异，但 N=2 能让重命名与元数据刷新同时被认领，显著降低元数据排队与完成延迟。

---

## 测试集规模与测量口径

- **测试集规模**：74 个成员目录，共 23,094 个普通文件（总计约 71.36 GiB），包含 1,510 个音频条目。大量事实缺失场景清空副本码率，单会话实际触发补测 1,473 个音频文件。
- **存储与挂载**：媒体库位于远端 SATA HDD（Btrfs），通过只读 CIFS / SMB 3.1.1 挂载访问；SQLite 数据库运行于本地 NVMe 独立副本（不使用内存盘）。
- **对照方法**：每组正式对照采用 5 对基线 / 候选，按 AB / BA 顺序交替执行。不剔除异常值，不并行运行其他测试或负载。
- **计时与资源口径**：
  - 完成时间从整批入队前起算，包含排队、规划分析与持久化（含最多约 5 ms 轮询误差）；`Queue` 仅统计 dispatcher 认领前的排队等待。
  - 阶段耗时为各次调用累计值，存在并发重叠或背压等待，不可直接相加替代端到端耗时。
  - CPU 为 `wait4` 统计的测试进程及已等待子进程累计值；`wait4` RSS 为单进程最大驻留集统计（多进程并发瞬时内存通过独立的进程树 `smaps_rollup` 采样补充评估）。

## 第一轮：瓶颈定位与基础链路优化（热缓存）

### 1. 瓶颈定位与数据库锁修复
在初始单会话（事实齐全）样本中，总耗时约 2.77 s，其中输入刷新占 2.66 s（SQLite merge 阶段占 1.77 s），实际计划分析仅 0.095 s。此外，真实负载并发压测暴露出两类底层问题：
- **新连接读阻塞（`SQLITE_BUSY`）**：原实现在每次建立连接时重复执行文件级 `PRAGMA auto_vacuum`。当存在活跃写事务时，新建立的只读连接会因尝试获取写锁而阻塞。修复为仅在创建空库时初始化增量回收模式。
- **选中范围合并（Merge）慢查询**：原实现按每个 scope 重复构造完整路径列表并进行全表范围扫描。优化为单次构造索引范围校验，并按 staging 主键逐项清理过期条目，Merge 中位数由 1.781 s 降至 0.237 s。

### 2. 扫描错峰（单扫描槽）与内部宽度筛选
- **单变量验证**：
  - 将单作品缺失码率探测宽度从 4 降至 2 时，探测并发峰值减半（16→8），但端到端耗时从 5.983 s 退化至 6.498 s（+8.6%），故保留内部作品分析宽度 4、单作品探测宽度 4。
  - 为转换 Task 的输入刷新引入跨会话单扫描槽（每次 walk 宽度 32），将多会话并发时的目录遍历峰值从 64 限制为 32，避免机械盘 I/O 恶化，同时允许分析阶段继续跨会话重叠。

### 3. 首轮组合优化对照结果（5 对交替，热缓存中位数）

| 场景与指标 | 原始基线 | 首轮实现 | 变化与说明 |
| --- | ---: | ---: | --- |
| 单计划、事实齐全（总耗时） | 2.941 s | 1.391 s | -52.7%，主要来自消除重复 SQL 工作 |
| 同上：Merge 阶段耗时 | 1.781 s | 0.237 s | -86.7% |
| 四计划共享磁盘压力（首请求完成） | 5.520 s | 1.365 s | 扫描错峰显著改善首请求响应 |
| 同上：整批完成 | 11.299 s | 5.138 s | -54.5%，扫描 walk 峰值由 64 降至 32 |
| 两个转换 + 轻量任务（重命名完成） | 5.766 s | 1.514 s | 排队与阻塞改善 |
| 同上：元数据完成 | 5.619 s | 1.844 s | 排队与阻塞改善 |
| 同上：整批完成 | 5.778 s | 2.551 s | 5 对均改善 |
| 单计划、大量事实缺失（总耗时） | 6.112 s | 4.427 s | 1,473 个文件补测，ProbeErrors = 0 |

## 第二轮：轻量规划通道与受控冷/热缓存全面对比

### 1. 机制演进：轻量规划专用通道
首轮优化后，当通用 worker（默认 2）被两个重型转换计划占满时，后续提交的重命名与元数据刷新仍需排队数秒。为此引入可选接口 `LightPlanner`：
- 重命名与元数据刷新声明为轻量规划任务，由新增的 1 个固定宽度专用 worker 认领；
- 通用 N 个 worker 仍按跨类型 FIFO 认领所有任务，未声明为轻量的任务仅走通用通道。

在 N=2 热缓存机制对照（5 对交替）中，引入轻量通道后：
- **重命名完成中位数**：由 1.720 s 降至 **0.377 s**
- **元数据完成中位数**：由 1.881 s 降至 **0.551 s**
- **混合负载整批完成**：由 2.787 s 降至 **2.573 s**

### 2. N=1 / 2 / 4 并发宽度对比（热缓存与受控 OS 冷缓存）
本轮共采集 **240 个正式样本**（包含热缓存与受控 OS 冷缓存下的 1↔2、2↔4 配对交替测试，机制对照及双盘边界测试）。冷测在每轮句柄关闭后同步清理服务端与客户端 OS 页面缓存（磁盘处于旋转就绪态，不含休眠唤醒延迟）。

### 3. 双独立 HDD 扫描边界
在另一块独立 SATA HDD 上克隆相同规模的数据集（74 个目录、23,094 个文件、约 71.36 GiB），测试两盘同时提交转换计划：
- **热缓存**：单盘分别耗时 1.302 s / 1.320 s，同时提交整批耗时 2.387 s（配对增幅中位数 +90.4%）。
- **冷缓存**：单盘分别耗时 4.237 s / 7.386 s，同时提交整批耗时 11.679 s（配对增幅中位数 +65.5%）。
由于扫描槽跨所有转换会话全局共享、不按物理设备区分，多盘并行扫描会被串行化。该表现作为已知架构边界记录，不为此引入设备拓扑识别。测试完成后已清理克隆数据集。

## 第三轮：实际单库部署形态补测与定案

### 1. 目标负载收敛
结合实际产品约束：媒体库位于同一机械盘，用户不同时规划多个库；单库对应单一 Workset，且同一类 Operation 至多存在一个排队或运行中的生成会话。因此**实际同时运行的转换计划至多为 1 个**。

本轮针对真实的“1 个转换计划 + 1 个目录重命名 + 1 个元数据刷新”并发提交场景，在热缓存与受控 OS 冷缓存下分别执行 N=1 与 N=2 的 5 对交替测试（共 20 个正式样本）。

### 3. 最终定案理由
1. **整批吞吐无显著差异**：整批完成时间完全由转换计划决定，N=2 在热测与冷测中仅分别胜出 3/5 对和 2/5 对，未形成一致的吞吐优势。
2. **消除轻量任务间的相互排队**：当 1 个转换计划占用 1 个通用 worker 时，若 N=1，重命名与元数据只能串行共享唯一的轻量通道（导致元数据排队等待 0.316 s ~ 0.677 s）；而 **N=2 保留了第 2 个空闲通用 worker**，可与轻量 worker 同时认领重命名和元数据任务，使元数据排队降至约 0.012 s ~ 0.014 s，完成时间在热测中缩短 40.7%（5/5 胜）、冷测中缩短 52.5%（4/5 胜）。
3. **代价可接受**：N=2 在热测下因两项轻量任务并发访问目录与数据库，重命名耗时增加约 63 ms（0.321 s → 0.384 s），但两项轻量任务在热缓存下均稳定处于亚秒级（< 0.4 s）。因此保留默认 `GenerationConcurrency = 2`，不向前端暴露多余的内部并发调优开关。

## 复现入口

在 `backend/go` 目录下使用独立的静态数据库备份运行测量测试：

```sh
CONCURRENCY_MEASURE_DB=/path/to/backup.db \
CONCURRENCY_MEASURE_WORKSETS=workset-id \
CONCURRENCY_MEASURE_ROUNDS=5 \
CONCURRENCY_MEASURE_SESSIONS=2 \
CONCURRENCY_MEASURE_SCAN=32 \
CONCURRENCY_MEASURE_OUTPUT=/path/to/results.json \
TMPDIR=/path/to/local-disk-tmp \
go test ./internal/conversion -run '^TestMeasureGenerationConcurrency$' -count=1 -v
```

可选环境变量：
- `CONCURRENCY_MEASURE_MISSING=1`：在测试副本中清空码率以触发缺失事实补测。
- `CONCURRENCY_MEASURE_COPIES=4`：克隆多个共享同目录的工作集以模拟多会话压力。
- `CONCURRENCY_MEASURE_LIGHT=1`：同时提交重命名与元数据刷新任务（需备份库内含对应操作草稿）。
