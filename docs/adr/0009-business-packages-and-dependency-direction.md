# 0009 业务分包与依赖方向

后端原来按「层」组织：`internal/repo/sqlite`、`internal/httpapi`、`internal/usecase`、`internal/tasks`、`internal/services`。分层的名字掩盖了实际形状——HTTP 处理器直接持有 `*sqlite.Repository`，工作集用例在自己身上定义记录类型，转换任务在 `sqlite` 包里读写 `entries` 表；包的边界不是业务的边界，改一条业务规则要在三四个目录之间来回。

这次重构选择了**按业务分包，由消费者声明端口**，以便一条业务规则的类型、用例和依赖可以一起修改。下文记录当时的迁移范围、边界选择及保留的行为。

## 1 从具体存储依赖改为消费者端口

迁移后的依赖形状是 `app → adapters → business → pathnorm`。当时的业务模块（`library`、`inventory`、`workset`、`conversion`、`fileops`）接收 `library.Store`、`workset.Store`、`conversion.Inventory` 等消费方接口，替代对具体 `*sqlite.Repository` 的依赖；`internal/adapters` 实现这些接口，`internal/app` 装配它们。`internal/arch` 的依赖测试让这次迁移建立的边界可以被检查。

端口选取了消费方实际调用的方法，同一个 Repository 因而可以满足多个接口。这避免了业务模块因共享存储实现而互相依赖，也没有引入按表拆分的 Repository 或为未来用途预留的方法。

## 2 复合事务保留在 SQLite 内

「替换当前记录」「发布新计划并退役旧计划」「带条件创建执行会话」「同步库存及生成凭据」「整批 staging 原子写」在迁移时各自保留为一个事务和一个端口方法。调用方无法在几次独立读写之间重新建立其不变式，因此重构调整了端口边界，没有拆散事务。

## 3 库存读写归入 inventory

扫描合并、执行后的库存同步、码率回写都围绕 `entries` 的观察事实，`conversion`、`workset` 与浏览路由消费同一份事实。这次重构将库存读写接口归入 `inventory`；`library` 保留媒体库、根变更/删除规则与目录身份（`dir_id`）。边界依据这些事实的生命周期划分，而不是让浏览入口和转换任务各自拥有一份库存模型。

## 4 工作集生命周期与任务载荷分离

迁移将操作生命周期（身份、归属、版本、草稿、修订、计划、执行会话）及 `Task` 接缝放在 `workset`，由 `conversion` 实现任务。记录、成员、草稿、修订、计划、执行会话和 `CanonicalJSONHash` 随生命周期一起搬迁，任务载荷则保留为不透明 JSON。这使工作集可以管理操作而不解析转换策略，避免了 `workset → conversion` 的反向依赖。

## 5 迁移保留冻结数据的字节表示

这次结构迁移保留了 `CanonicalJSONHash` 的规范化（`UseNumber`、键排序、数组保序、原始字节回落）、草稿文档 schema v1、NUL 连接的标签快照、`{delete_mode}` 会话选项和逐组件结果行的字节表示。它们已经落库；同时调整格式会改变旧哈希、幂等重放与历史修订的读取，使包迁移变成数据契约变更。

## 6 迁移保留准入时机

迁移保留了进程级准入对「扫描 / 规划 / 执行」与「直接文件管理」的互斥，以及在响应提交前申请的时机；否则 409 会变成 200 之后流内的一条 `event: error`。三种扫描入口也没有被归一为一次 `Acquire`：全库扫描先查「执行中」，页面成员刷新只取扫描槽，写后刷新两者都不取，因为它已在槽内。这些区别影响可见行为，不属于结构迁移的调整范围。

## 7 请求路径改为经过业务入口

重构将 `internal/adapters/httpapi` 对存储适配器的直接调用替换为业务入口调用。策略完整性、槽名长度、标签有效性等判定随所属业务模块搬迁，处理器保留请求解码及结果到状态码、错误码的映射。这让同一条业务规则可以被请求路径和其他调用方共同使用。

## 被否决的替代方案

- **先搬全部类型、再立接口（水平五阶段）**：搬类型的同一刻 `sqlite` 需要 `workset` 的类型，而 `workset` 仍需要 `sqlite.Repository`，互相 import。原文用「短期别名」绕开它，但本模块没有 `internal/` 之外的消费者，别名纯属额外工序与待删残留。改为垂直切片：类型与端口同步落地。
- **按表拆 Repository（`LibraryRepository`、`EntriesRepository`…）**：表不是业务边界，一张表常被多个模块读写；按表拆会把 §2 的复合事务拆散，并把「谁拥有这张表」这个问题原样留下。
- **让 `httpapi` 依赖具体的 Repository，只把 SQL 挪进方法**：请求路径仍旧直达数据库，业务规则（准入顺序、错误码）继续散在处理器里；这正是重构要消除的形状。
- **在这次迁移中为 `rename_noreplace_*.go` 单独造一个端口**：当时三个未导出平台文件只有 `fileops` 一个消费者，单独搬迁没有带来共享能力，只增加一个端口；因此不在这次重构范围内。
