# 0010 暂不引入全局单写入口

## 背景

SQLite 数据库在底层原理上同一时刻只允许一个写事务。但这本身不足以证明应用需要再建立全局单写入口（单写协程或命令队列）。

## 决定

1. **维持当前连接池与局部并发控制**：
   - 继续沿用标准连接池，搭配 WAL 模式、`BEGIN IMMEDIATE` 显式排他写事务、合适的 busy_timeout 以及关键写场景的轻量重试机制。
   - 业务准入已经限制了部分任务重叠（扫描、执行与文件管理互斥）。
2. **基于实测证据暂缓重构**：
   - 根据在准入控制与并发场景下的实测数据（参见测量报告），35 次综合运行测试中没有出现任何 `SQLITE_BUSY` 或锁死错误，关键路径的 `BEGIN` 耗时 p99 均低于 9ms。
   - 引入专用单写协程需要解决读写连接池切分、事务嵌套重入、文件操作后的回调通知以及上下文超时撤销等复杂问题，在收益未验证时不增加这些契约。

## 放弃的方案

- **现在引入统一单写连接或命令队列**：需要处理读写池边界、重入和文件发布后的数据库收尾，而现有证据未显示它能解决实际故障。若将来证实需要统一串行化，优先评估私有单连接写池与独立只读池；命令 Worker、FIFO 和 group commit 带有额外语义与成本，本次没有验证其必要性或批量收益。
- **用强制竞争结果论证改造**：另一连接持写锁 5.5 秒时应用返回 `SQLITE_BUSY`，但这属于外部竞争，进程内单写入口无法消除，需要另行处理。

## 后果与重新评估触发条件

- 目前系统不引入统一单写 Goroutine。
- 若未来出现以下条件之一，应重新开展评估与基准测量：
  1. 真实准入负载下出现进程内的 `SQLITE_BUSY`；
  2. 同一路径单次运行至少 100 个 `BEGIN` 样本的 p99 达到 2.5 秒。稀疏路径的最大等待接近该阈值时，先补充测量。
- 触发条件 1 曾在 5,000 成员负载下出现（夹具绕过 2,000 成员上限）：根因是选中范围库存合并在单个事务中随范围增长持锁数秒，改为按成本预算分批提交后，同一负载复测无 `SQLITE_BUSY`，多次复测中任一写事务单次持锁最大约 145 ms。由此不重新评估单写入口。
- 后续功能改变并发模式、数据规模或事务长度时，按新的实际负载重新测量。
- 完整测量方法与统计数据参见 [sqlite-write-contention-measurement.md](../issues/sqlite-write-contention-measurement.md)。
