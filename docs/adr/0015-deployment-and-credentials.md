# 0015 部署形态与凭证投递

## 背景

Preen 需要同时服务个人 NAS／家庭服务器上的浏览器部署，以及由宿主外壳托管的桌面形态。浏览器部署需要一个可独立运行、同源访问页面、API、媒体和事件流的服务；桌面形态仍需保留自己的页面托管、凭证投递和进程生命周期接缝。首版部署边界是可信局域网、单个共享访问密钥，不引入公网服务或多用户会话管理。

## 决定

1. **由 Go 后端同源托管前端**：一个容器提供页面和后端服务，减少部署组件；API、媒体和事件流共享浏览器来源与凭证，不要求用户额外维护代理服务。
2. **前端产物按目录托管**：后端使用构建后的前端目录，后端的日常构建与测试不依赖前端产物；桌面外壳可以托管同一份前端资源。
3. **浏览器凭证使用 HttpOnly cookie**：页面脚本不读取或保存共享密钥，浏览器原生的媒体加载与请求自动使用同源凭证。自动携带 cookie 也带来跨站请求风险，因此 cookie 认证的写请求需要同源校验。
4. **cookie 无服务端会话状态**：凭证代表共享密钥，服务重启不撤销登录，更换密钥统一使旧凭证失效。单密钥部署不需要会话数据库，接受无法单独吊销某个浏览器会话的限制。
5. **按运行形态投递凭证**：浏览器形态使用 cookie，桌面形态保留 Bearer 及媒体访问所需的凭证投递。桌面页面来源与 API 可能跨站，不能依赖浏览器的 cookie 行为；两种形态共享同一认证边界。
6. **进程默认是独立服务**：独立启动不依赖 stdin 或父进程存活；由宿主托管时显式启用 stdin 关闭触发有序退出的接缝。宿主关闭管道即可释放服务，也为没有 Unix 信号语义的宿主保留退出方式。
7. **认证状态切换采用整页导航**：凭证失效、登录成功和退出都创建新的页面生命周期，统一丢弃查询缓存、订阅、播放器、在途请求和全局状态。新文档重新建立订阅，避免认证恢复后遗留已停止的循环或退出后展示旧数据。
8. **默认配置由后端首次启动投递**：初始内容只有一个来源，开发、测试、容器和桌面启动均由后端负责。只在配置不存在时投递；投递后配置归用户所有，升级默认值不覆盖已有设置，也不以默认配置替换损坏文件。

## 放弃的方案

- **单独运行 Nginx 容器**：为同源托管增加服务、代理配置与生命周期管理，当前局域网单实例部署没有需要它承担的额外职责。
- **把前端产物编入 Go 二进制**：会让后端构建与测试依赖一次前端构建，并耦合桌面外壳与服务端的资源打包方式。
- **使用 sessionStorage 或 localStorage 保存浏览器密钥**：页面脚本可读取密钥；原生媒体请求又不能直接读取这些存储，需要额外传递凭证。localStorage 还会长期保留脚本可访问的秘密。
- **维护服务端会话表**：引入会话持久化、清理和吊销机制；单个共享密钥没有独立用户身份，不足以支撑这套额外状态的成本。
- **所有形态统一用 cookie 或统一用 Bearer**：前者依赖桌面跨站 cookie 的可用性，后者要求浏览器脚本持有密钥并为原生媒体访问另行投递凭证。
- **默认监视 stdin 或轮询父进程**：独立服务可能没有可持续读取的 stdin，也不应因启动它的终端或父进程退出而结束；显式宿主管道已经表达了生命周期所有权，无需另建父进程检测机制。
- **在单页内逐项拆除并恢复认证状态**：清理范围分散在缓存、store、订阅与播放器中，容易漏掉在途请求或无法自行重启的循环；整页生命周期提供统一边界。
- **由启动器复制默认配置，或由镜像入口脚本写入**：不同入口会出现默认值和首次启动行为分歧，遗漏测试或桌面等入口；配置初始化属于应用启动责任，不应由每种部署各自实现。

## 后果

- 浏览器凭证泄露等同共享密钥泄露，只有更换密钥才能统一吊销；HttpOnly 不提供传输加密。可信局域网可使用 HTTP，需要传输保护时由已有反向代理提供 HTTPS。
- 认证切换会中断当前页面活动并丢弃未保存的界面状态，这是统一清理边界的代价。
- 服务端部署需要同时交付后端和前端目录；具体线协议与访问规则由 [common.md](../api/common.md) 记录。
