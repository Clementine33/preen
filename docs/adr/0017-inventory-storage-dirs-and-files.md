# 0017 库存存储：目录表与文件表分离

## 背景

库存表 `entries` 以完整路径为主键，每行另存 `parent_path`、`name`、`root_path`，并为父路径和 `(root_path, is_dir, path)` 各建一棵索引。在 8.7 万行的开发库上，库存及其索引占全库约 98%（约 122 MB）：平均 220 字节的路径在行与索引中重复存储 5 次以上。当前真实库约 20 万文件，目标需支撑 100 万文件。

## 决定

1. **目录与文件分表**：目录表每个目录一行，保存完整路径（唯一）、所属库根、作品根标记与收录时间；文件表只保存所属目录的整数代理键与文件名，主键为二者组合并采用 `WITHOUT ROWID`。删除目录级联删除其文件。
2. **代理键不出存储适配层**：对外身份仍是路径与 `rel_path`；领域类型、HTTP 契约与按路径关联的其他表（生成记录、作品副本绑定）不感知代理键。它也不是 [CONTEXT.md](../../CONTEXT.md) 中的目录身份 `dir_id`。
3. **子树查询走目录路径范围**：在目录表上按路径前缀范围选出子树目录，再按代理键连接文件；不存父目录键，不用递归查询。
4. **扫描暂存表不归一化**：暂存行是一次合并内的临时数据，继续按完整路径记录，合并在同一事务内先写目录再写文件。
5. **只存有读者的列**：只写不读的扫描标识、脏标记、错误字段与更新时间不进入新结构；收录时间以整数秒存储。

开发库实测（同一份 87,011 行数据）：整库由 123.4 MB 降至 10.8 MB；最大库根的作品列表查询由 19 ms 变为 17.5 ms；重命名最大作品目录时需改写的行数由子树全部条目（2,349 行）降为子树中的目录行。

## 放弃的方案

- **sqlite-zstd 压缩扩展**：B-Tree 索引无法压缩，而索引占空间大头；单行写入需重压整块；扩展需随平台分发原生库，破坏纯 Go 构建。
- **DuckDB／Parquet**：列式不可变存储不适合库存的高频单行更新；与其余 SQLite 表的合并无法共处一个事务；驱动依赖 CGO。
- **只做表内瘦身**（`WITHOUT ROWID`、删冗余列与索引，保留完整路径主键）：实测降至 29.3 MB，改动小，但 100 万文件约 340 MB，目录重命名仍需改写整棵子树的文件行。
- **目录与文件共存一张表、另建目录字典**：每个目录在字典与条目表各存一行，仍需类型标记，体积与查询均不优于分表。
- **目录只存父键与名称**：子树查询全部变成递归查询，换来的空间只是目录完整路径（约占库存行数的 12%）。
- **保留名为 `entries` 的兼容视图**：视图上按拼接路径的条件无法使用索引，查询会退化为全表扫描。
- **物化作品根的文件数与音频数**：能把作品列表压到毫秒级，但合并、直接文件管理与执行提交都要负责维护计数。在单库根 104.6 万文件、4 万作品根的放大数据上，现算计数加上写入时由数据库维护的音频标记约 430 ms（单算文件数的子树扫描下限约 270 ms），当前约 20 万文件的库按线性估算约 90 ms，暂不值得承担维护成本。

## 后果与重新评估触发条件

- 按路径的点查需先在适配层拆分为目录路径与文件名；集合查询以「目录路径 + `/` + 文件名」与其他表的路径比较。
- 若 100 万文件规模下目录表本身成为瓶颈，或出现必须按父子关系遍历的查询，再评估父目录键。
- 若真实库上作品列表查询超过约 300 ms，再评估物化计数。
