# 0020 线格式契约：由 Go 类型生成 JSON Schema

## 背景

HTTP/SSE 的线格式曾有三处各自维护的描述：Go 侧的 json 标签（分散在 `adapters/httpapi` 和直接被序列化的领域类型里），前端手写的请求/响应类型，以及 `docs/api/*.md` 的文字说明。三者之间没有机器检查：后端 handler 测试用零散的键断言检查响应，前端测试自己 mock fetch，客户端用 `response.json() as T` 直接信任响应。改了一侧，另一侧的测试照样能过。代码越来越多由 AI 生成，这种不被察觉的漂移风险正在变大。

[0015](0015-deployment-and-credentials.md) 规定前端产物由同一个服务同源托管、随同一个包发布，所以新加载的页面总是和服务同一版本。唯一的例外是服务升级时仍然开着的旧标签页：旧版 JS 会继续请求新后端，同源托管不会替换正在运行的页面。除此之外，漂移都发生在开发和构建阶段，应当在 CI 里拦住，而不是等到运行时。

## 决定

1. **Go 是线格式的唯一来源。** 线上出现的每个 JSON 请求体、响应体（包括错误信封）和 SSE 事件载荷（包括 error 事件）都由具名类型表达，不用匿名结构。schema 的根类型在 `adapters/httpapi` 里声明；与领域类型逐字段一致的线上类型以领域类型定义（`type X works.Y`），不手工复制字段；有实际处理的转换（nil 规整为 `[]`、自定义 `MarshalJSON`、视图选择、三态解码、字段改名或省略）留在 httpapi。领域类型的改动导致线格式变化，由入库的 schema、`task contract:check`（重新生成后必须零 diff）和生成的 TS 类型暴露出来。
2. **结构由生成的 JSON Schema 表达。** 从 httpapi 的具名类型生成 Draft 2020-12 JSON Schema，按类型分别入库到 `docs/api/schema/`，请求与响应分别建模；HTTP 状态码和 SSE 事件到 schema 的绑定单独生成。schema 描述实际的序列化结果：自定义 `MarshalJSON` 的类型用手写的 schema 覆盖，PascalCase 的 FileTuple 等既有编码如实保留，生成时不做美化。生成器和校验库只被测试与生成代码引用，不进入生产包。
3. **不透明载荷按 Task kind 分别建 schema。** [0004](0004-task-seam-and-opaque-payloads.md) 中以 `json.RawMessage` 传输的 Task 载荷和设置，外层 schema 只能看到一个不透明字段。每个 Task kind 和 `schema_version` 的组合有自己的载荷 schema（`<kind>_v<version>_<name>`），由各 Task 包的具名类型生成；外层 schema 按 kind 引用对应的载荷 schema。判别沿用已有字段（如 metadata_refresh 结果的 `stage`），不为 schema 增加线上字段。前端契约在收到响应前就要选定，所以每个 kind 只绑定一个版本；出现第二个版本时生成失败，由引入者决定前端如何区分。
4. **职责划分。** schema 负责字段、类型、可选与可空，以及封闭字符串取值集合（`enum`）；`docs/api/*.md` 负责语义、行为、错误码、准入与版本规则，并链接到对应的 schema，不再重复字段的类型说明。`enum` 由 Go 侧给出：命名字符串类型提供 `WireValues()`，其余字段用 `jsonschema:"enum=…"` 标签，前端不手写字面量联合来补。
5. **后端测试按 schema 校验。** httpapi 测试和 e2e 测试用同一个辅助函数，把请求体、成功响应、错误响应和 SSE 事件载荷对照 schema 校验。键断言只保留在检查语义值的地方。
6. **前端 wire 类型由 schema 生成。** 生成的类型取代手写的请求和响应 DTO，只有路径参数、查询参数、客户端契约和配置类型仍然手写。客户端对数据的整形（例如把已存载荷中为 `null` 的标签列表补成 `[]`）放在 wire 类型到视图类型的一层，视图类型以生成类型为基础，组件只使用视图类型。
7. **运行时校验只在开发和测试环境启用，契约由调用点指定。** 泛型参数在运行时不存在，所以每个 API 方法要显式传入契约：HTTP 按状态码分别对应成功 schema 和错误信封，SSE 按事件名对应载荷 schema，Task 相关的契约按 kind 选择。开发、Vitest 和经 Vite 运行的 Playwright 中，校验器从入库的 schema 按需编译；调用点的编译期条件让生产构建剔除校验入口、契约元数据和 AJV，构建后逐模块检查。服务升级时旧标签页和新后端之间的错配风险，接受下来，由用户刷新页面消除，不在生产环境做校验。

## 放弃的方案

- **前端手写 zod schema**：会成为 Go 类型、TS 类型之外的第三个来源，而且后端测试读不到它，拦不住后端漂移；放到生产环境运行，能拦住的只有升级时旧标签页的错配，代价却是作品墙这类大列表每次都要多解析一遍；这种错配更适合靠刷新页面解决。
- **Go 直接生成 TS 类型（例如 tygo），不产出 schema**：前端能得到类型，但后端测试和脚本客户端没有可以执行校验的产物；自定义 `MarshalJSON` 的实际形状也无处表达。
- **完整的 OpenAPI 描述（包括路由、参数和认证）**：覆盖面大，但路由、准入和错误语义已经由 `docs/api/*.md` 承担，再全部迁过去成本高、收益低；只把结构机器化就能解决漂移问题。
- **以 TS 类型为来源反向约束后端**：线格式由后端决定，以前端为来源会让后端测试依赖前端构建，与 0015 中“后端构建和测试不依赖前端产物”的考量相冲突。
- **维持现状，靠键断言和人工同步**：原有大约 300 处零散断言，覆盖不完整、无法审计，前后端之间也没有任何联系。
- **httpapi 独占线上类型，并由 `arch` 测试（go/types 检查 writeJSON、请求解码和 SSE 发送的实参类型）强制**：漂移已被入库 schema 的零 diff 检查覆盖，领域类型一改，schema 和生成的 TS 类型立刻变化，所以这条边界作为防漂移手段是冗余的；代价是约 1200 行逐字段复制的转换代码，加上约 400 行的检查器及其违规用例。
- **把 AJV standalone 生成的校验器入库**：产物约 3.2 MB，会撑大仓库历史，还必须与 schema 同步重新生成；开发和测试中直接用入库的 schema 按需编译，校验效果相同，且没有生成物需要维护。
- **前端按响应里的 `schema_version` 选择 Task schema**：契约同时用于请求和 SSE，在响应到达前就已选定；目前每个 kind 只有一个版本，按版本分派没有收益。

## 后果

- 以领域类型定义的线上类型，其字段和 json 标签随领域类型变化，改动由 schema 零 diff 检查暴露；未在 httpapi 声明为 schema 根的领域类型，不在 schema 覆盖范围内。
- 新增一个 Task kind 或提升载荷的 `schema_version` 时，必须同时提供它的载荷 schema；提升版本还要先决定前端的版本区分方式。
- 服务升级时还开着的旧标签页，在刷新前可能把新响应按旧结构解析。
- 开发依赖增加：Go 侧一个 JSON Schema 生成库和一个校验库，前端一个 schema→TS 生成器和一个校验器。
- 可空性会被如实暴露。httpapi DTO 的数组字段从不为 `null`，空集合是 `[]`；存储的 Task 载荷可能仍含 `null` 数组，它们的 schema 如实保留可空。约定见 [common.md](../api/common.md#wire-schemas)。
- 封闭取值集合在 Go 常量和 `enum` 标签之间存在重复，靠测试期 schema 校验和生成的 TS 类型兜底，不另设一致性检查。
- 脚本客户端可以直接使用入库的 schema。
