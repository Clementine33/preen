# 0011 开发 schema 与发布迁移双轨

## 背景

在单机 Monorepo 项目中，开发阶段数据库字段和表结构频繁变动，若每次改动都生成不可变迁移脚本，会导致迁移文件迅速膨胀并产生大量无意义的临时版本；但一旦软件发布到最终用户手中，又必须保证数据库具有可靠、确定且无损的数据升级路径。

截至 2026-10-23，项目已发布 v0.1.0–v0.1.2（最新 v0.1.2 发布于 2026-05-04）。这三个版本使用旧 internal/repo/sqlite 结构，不包含当前 works 目录或 `00008_initial.sql`。本记录的“未发布基线”特指当前 works／编号 8 结构，不能理解为整个项目从未发布。v0.2.0-rc.1 携带编号 8，但仅作者自用、未公开发布，不构成分发。

## 决定

1. **开发与发布双轨生命周期（Dual-track Lifecycles）**：
   - **开发模式（`X.Y.Z-dev`）**：以 `schema.sql` 直接描述最终库表结构。开发期遇到结构变动可自由修改 `schema.sql`，通过重建脚本（`task db:rebuild:dev`）重置本地数据库，不做自动修复。对尚未随版本交付的当前 works／编号 8 基线，大型 schema 重构也采用开发库显式重建；不为未发布中间结构设计复杂数据迁移、异常旧数据回填或双结构兼容。
   - **发布模式（正式 Release 及 RC，无论是否公开）**：完全由嵌入式 `goose` 迁移脚本（`internal/adapters/sqlite/migrations/`）管理。当前基线首次公开发布前将最终结构收敛到单个编号 8 的初始迁移；未发布基线可随开发结构继续修改。冻结点是首个公开版本（RC 或正式 Release）：此后该迁移的文件名、编号及内容即刻冻结，后续变更只追加迁移。未公开的 RC 不冻结迁移，迁移改动后其数据库重建，不提供升级路径。
2. **两类数据库互不转化与拒绝跨代升级**：
   - 数据库文件显式标记自身模式，开发库与发布库禁止互相覆盖转换。
   - 发现数据库迁移版本高于当前程序支持的最大版本时，拒绝启动，不把未知结构当作可升级基线。
   - 已发布 v0.1.x 的旧库不是开发库，也不属于本轮重建目标；本轮不提供从该旧结构到编号 8 的升级路径。保留旧库供对应旧程序使用，当前开发程序使用新的开发数据目录，不把旧库当作空库执行初始建表，也不手工改版本号。
   - 当前迁移体系中的旧未发布版本 1–7 不转换（这些迁移号不是 v0.1.x 发布版本号）：尝试版本 8 时先备份，再由已有表与初始建表冲突导致事务失败。原库数据和版本保持不变，启动失败；不忽略冲突或手工改版本。
3. **升级前原子备份（VACUUM INTO）与仅向上迁移（Up Only）**：
   - 已有数据的发布库在执行迁移前，通过 SQLite 原生 `VACUUM INTO` 备份当前包含 WAL 在内的完整物理副本。直接复制主数据库文件可能漏掉 WAL 中的提交，因此不用它做恢复基线。备份或迁移失败阻止启动。
   - 升级只走 `Up`，恢复不依赖 `Down`：个别迁移文件可能带有 goose Down 段，但它不是受支持的回退路径。升级故障通过恢复备份并换回旧程序解决；备份不自动清理。

## 放弃的方案

- **全程单一迁移流（每次字段改动均追加 migration）**：在特性分支高频迭代期间会产生大量零碎迁移和合并冲突。
- **由 ORM 自动检查 Diff 并执行动态 DDL**：SQLite 的 ALTER 能力有限，列重命名与类型推断靠猜，容易破坏数据。
- **以首个外部 RC 为冻结点**：仅供作者自用的 RC 也会冻结迁移，迫使预发布期为从未公开的结构追加迁移；这类数据库由作者自行重建即可，没有需要保护的外部用户数据。
- **维护双向 Down 迁移**：对于涉及列删除或数据重组的迁移，Down 脚本往往无法还原已丢失的列数据，给用户带来虚假的安全感。

## 后果

- 开发者必须明确当前运行环境与版本号；当前基线首次公开发布前同步维护 `schema.sql` 和唯一的未发布初始迁移，验证两轨结构及读写行为一致。旧测试库应使用对应旧程序或新数据目录。
- 详细迁移编写与发布检查规则见 [backend/go/AGENTS.md](../../backend/go/AGENTS.md)。
