# 缩略图服务：可丢弃的派生缓存与可替换的缩放引擎

## 1 背景与边界

作品详情页的胶片带与叠卡要为一组插画（常见数十到数百张、单张数 MB）同时显示缩略图。回环或局域网部署下，浏览器直接取原图、用 `createImageBitmap` 缩放可用，但它把每张原图的完整传输与解码推给客户端；云部署下带宽与客户端内存都不成立。这是技术债，不是能力边界。

决定：缩略图由服务端按需生成，经 HTTP 与可丢弃缓存复用；任何节点都不维护缩略图卷（扫描时预生成、持久化并需与媒体库同步的派生文件集）。

## 2 媒体事实：扫描之后后台测量

图片宽高与音频时长随清单文件条目存于 `entries`，与 `bitrate`、`format` 同级。前端在像素到达前即可排版：标本框贴合真实比例，胶片带等高、宽度随比例。尺寸是元数据，不是缩略图，不改变 §1 的决定。

- **不在扫描内测量**：扫描合并后即完成。合并（全库扫描、成员刷新）与进程启动各触发一次后台补测；一次补测按路径游标把库存里所有仍未知的条目走一遍，跨库、跨根。测不出的保持 `NULL`（未知不是零），下一次触发再试，补测不循环。
- **不与扫描遍历争 I/O**：补测持有准入闸（ADR 0002 §2）的**可抢占后台槽**。它在扫描、直接文件管理、维护、排队或运行中的会话任一存在时被拒绝，稍后重试；反过来它从不拒绝它们——它们令补测停止，并等它最后一次写回落地后才开始。每 64 个文件写回一次，停止时再写一次，被抢占只丢正在测的那几个。
- **只读文件头**：图片用 Go 标准库 `image.DecodeConfig`；WAV 读 `fmt`/`data` 块（数据大小 ÷ 字节率），MP3 读首帧的 Xing/Info/VBRI 帧数，无 VBR 头时按恒定码率估算（与 ffprobe 对同类文件的估算一致）；M4A（MP4 容器的 AAC）只读盒子头找到 `moov`（无论在 `mdat` 前后），取 `mvhd` 的时长 ÷ 时间刻度——即去掉编码器预填充后的长度，与 ffprobe 报告的一致（ffmpeg 与 qaac 产物共 547 个文件逐一比对，误差 < 1 ms），`moov` 里的逐帧索引表从不读取。其余格式与不认识的头（RF64、流式 WAV、自由码率 MP3、碎片化 MP4、裸 ADTS AAC）交给 ffprobe，原生解析从不猜。
- **工具路径与规划一致**：仅在需要 ffprobe 兜底时读取最新的 `tools.ffprobe_path`；原生读头路径不读取配置。
- **提交后通知**：每批事实成功写回后发送 `changed` SSE（`{}`）；失败不通知。每个订阅者只有一个待处理信号，慢客户端合并通知，不阻塞补测。连接时先发一次信号补齐断线期间的变化，每 15 秒心跳，断开即注销。无需事件历史、数据库字段或通用事件总线。
- **码率一并记下**：有损编码音频（MP3、M4A/AAC、Opus）的 `bitrate` 也由补测写入，候选条件含“编码音频且码率未知”；写回只填测到的字段，已知值不被清空。MP3：Xing/VBRI 按 字节×8×采样率 ÷（帧数×每帧样本）还原平均码率，LAME Info 与无头恒定码率取帧头码率，无头且首几帧码率不一（无头 VBR）则交 ffprobe；M4A：仅一条轨、一个 `mdat` 时取 ⌊`mdat` 载荷×8×`mdhd` 刻度 ÷ `mdhd` 时长⌋，与 ffprobe 的 mov 公式一致（250 个文件逐一相同），否则交 ffprobe。转换规划的码率分析保留为兜底，只测库存里仍缺码率的条目，并调用同一个探测器，同一文件无论由谁测得都是同一个数。
- **并发 8**：每次只读数 KiB，网络共享与机械盘上并发能隐藏往返、让磁盘重排队列。实测（SMB 上的机械盘、未缓存文件）：原生 1 并发约 26 个/s，8 并发约 45 个/s，16/32 只再多 10–30% 而单个等待翻倍；ffprobe 最佳约 18 个/s。8 拿到大部分吞吐，并给共享盘的其他使用者留出余地。宽度是代码内可覆盖的字段（测试、基准用），不对外配置。

## 3 请求路径分层

1. **不可变地址**：缩略图地址带目标高度 `h` 与版本 `v = hash(大小, mtime, 内容修订, 引擎版本)`。`v` 由清单随每个图片条目给出（`thumb_v`），客户端不自行计算。`h` 向上取整到少数几档服务高度（120/240/480/960），任意高度既不碎化缓存，也不放大计算；源图矮于目标时不放大。只有成功响应及对应的 304，且 `v` 等于当前版本时才响应 `Cache-Control: private, max-age=31536000, immutable`（接口带 bearer 鉴权，故 `private`）；过期或缺失的 `v` 照常应答但标 `no-cache`，旧地址永远不会把旧字节钉在缓存里。`ETag` 为 `v` 加高度；503、422、500 等失败响应使用 `no-store`，不携带成功内容的 ETag。
2. **缓存命中**直接返回（§4）。
3. **合并**：同一地址的并发请求共享一次计算（singleflight）。
4. **准入**：同时计算数上限为 CPU 数，等待队列有界；队列满时返回 `503` 与 `Retry-After`。请求上下文取消即撤出排队；已获准入的计算不中止，跑完写入缓存——它由同一地址的所有等待者共享，一个客户端滚走不应让其余等待者与下一次访问落空。排队中的领头请求离开时，仍在等待的请求接替领头。缩略图是只读路径，不占 ADR 0002 的全局准入槽。
5. **引擎**：解码、缩放、编码（§5）。
6. **写入缓存**：先写临时文件再改名，读方不会读到半个文件。

服务端自保不依赖前端：第 3、4 层按「多客户端」设计，前端限流（§6）只减少无谓排队。

**安全**：源路径按成员目录的包含规则解析（与 ADR 0002 直接文件管理同一套：拒绝越界、符号链接穿越）。解码前用 §2 的宽高检查像素总数，超过上限（约 1 亿像素）不解码，前端显示排线占位，防解压炸弹。

## 4 缓存是可丢弃的派生物

缓存与卷的区别：缓存随时可整体删除，按需重建，不入数据库，无需与媒体库同步，也不需要清理任务追踪原图增删。

- 本地：数据目录下的 LRU 目录（`thumbs/`），有容量上限，按访问时间淘汰；访问时间记在文件 mtime 上（relatime/noatime 下 atime 不可靠），超出上限时淘汰到九成；运行中删除整个目录也安全。
- 云端：换成对象存储加 CDN，地址与第 1 层语义不变。

## 5 引擎端口

缩放引擎采用消费方声明的端口：输入源文件读取器与目标高度，输出编码字节与内容类型。

- **首个实现：纯 Go**。`image/jpeg`、`image/png`、`golang.org/x/image/webp` 解码，`golang.org/x/image/draw` 缩放；输出 JPEG，带透明通道的源输出 PNG。进程内执行，不产生子进程，也不引入新工具链。
- **升级路径：wazero 加 Rust WASI 模块**（`jpeg-decoder` 以 1/2 至 1/8 缩尺解码 JPEG，`fast_image_resize` 用 wasm SIMD 缩放），编译为 `wasm32-wasip1` 后以 `go:embed` 嵌入，实例池化。只在剖析显示解码是瓶颈时切换，只替换本层。
- 已知上限：PNG 无法缩尺解码，每次都要完整解码，因此重复访问的负载要靠第 1、4 层吸收，而不是靠引擎提速。

## 6 前端职责

- 胶片带与标本框按 §2 的尺寸排版，不等像素到达。
- 以带 bearer 头的 `fetch` 取缩略图（`<img src>` 带不了鉴权头），经 blob URL 显示；HTTP 缓存对 `fetch` 同样生效。
- 同时在途约 4 个请求，可见项优先；离开视口即用 `AbortController` 中止，使服务端对应的排队撤出（§3 第 4 层）。
- 收到 `503` 按 `Retry-After` 退避重试；允许的跨域响应显式暴露此头。
- 应用根部只维护一条 bearer 鉴权的补测通知连接；断线按 1、2、4 秒递增重连，上限 30 秒，401 停止重试，卸载取消连接和等待。每次通知刷新活跃作品清单与成员树，删除未活跃缓存。通知到达时先取消仍在进行的旧请求，防止其覆盖新事实。
- 扫描完成、文件操作、换库根和删库同步作品清单、详情与列表；缓存清单在详情页进入时立即绑定。相同作品的清单更新保留阅读、配对与播放状态，不重新启动音频。
- 缩略图 blob 按副本、路径、`thumb_v` 区分；版本变化撤销旧地址并重取。原图地址也带同一可选版本参数，让同路径更新触发元素重新加载。
- 过渡：服务落地前，允许浏览器直接缩放原图（`createImageBitmap`）。服务落地后删除该分支，不保留为长期的第二条路径。

路由与参数的最终形状在实现时写入 [docs/api.md](../api.md)。

## 拒绝的替代方案

- **浏览器缩放原图作为长期方案**：云部署下每张原图都要完整传输并在客户端解码，带宽与内存不可接受；只保留为 §6 的过渡。
- **维护缩略图卷**：扫描时预生成并持久化，需要与原图增删、改名、离线副本保持一致，同步与清理成本长期存在；缓存（§4）拿到同样的复用而不承担同步。
- **ffmpeg 子进程逐张缩放**：虽复用已有依赖，但每张图创建一次进程，高并发下进程数与 CPU 都会失控。
- **cgo 链接 libvips**：最快，但破坏 Windows 交叉构建（`task build:go:windows-x64`）。
- **libvips 编译为 WASM 在 wazero 中运行**：`wasm-vips` 面向 Emscripten 与浏览器，依赖 glib 与线程，WASI 下不可行；要走 WASM 路线，用 §5 的 Rust 模块。
- **JPEG 内嵌缩略图**：插画多为 PNG，且内嵌缩略图不可依赖。
- **请求取消即中止已开始的计算**：计算由同一地址的并发请求共享，领头者离开就中止会让其余等待者一并失败；撤出排队即可释放资源，已开始的计算跑完进缓存不浪费。
- **客户端自行计算版本、任意目标高度**：客户端没有 mtime、内容修订与引擎版本；任意高度使缓存碎化，且是现成的 CPU 放大器。
- **只靠前端限流保护服务端**：云端有多个客户端，单个客户端的礼貌无法约束总负载。
- **扫描内测量媒体事实，测完才算扫描完成**：网络共享或机械盘上数千个文件要数分钟，前端一直停在「扫描中」；刷新页面会取消扫描并丢掉全部测量，还延长了准入槽的占用。（§2）
- **补测占用可拒绝的普通槽（像维护那样）**：补测持续数分钟，期间用户点扫描只会得到 BUSY；补测该让路，而不是让用户等。（§2）
- **一律用 ffprobe 测时长**：为分析流它每个文件读取多达数 MB，未缓存的机械盘上并发越高越是来回寻道（32 并发 p95 约 5 s），最佳吞吐只有原生读头的约三分之一。（§2）
- **定时轮询未知条目**：测不出的文件会被反复探测，永远停不下来；只在有新事实可能出现时（合并、启动）触发。（§2）
- **M4A 取音轨 `mdhd` 或编辑列表 `elst` 的时长**：`mdhd` 含编码器预填充（ffmpeg 的 1024 个采样，约 21 ms），与 ffprobe 不一致；qaac 不写 `elst`。`mvhd` 两种产物都对。（§2）
- **引入 `abema/go-mp4` 解析 M4A**：只需按盒子头跳到 `mvhd`，手写约 40 行，与 WAV/MP3 解析同一写法；为此引入依赖不划算。（§2）
- **更高的并发（16、32）**：吞吐只多 10–30%，每个文件的等待翻倍，同一块盘上的播放与转换被拖慢。（§2）
