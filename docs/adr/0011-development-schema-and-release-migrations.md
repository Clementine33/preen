# 0011 开发 schema 与发布迁移双轨

## 背景

在单机 Monorepo 项目中，开发阶段数据库字段和表结构频繁变动，若每次改动都生成不可变迁移脚本，会导致迁移文件迅速膨胀并产生大量无意义的临时版本；但一旦软件发布到最终用户手中，又必须保证数据库具有可靠、确定且无损的数据升级路径。

当前数据结构以 `internal/adapters/sqlite/migrations/00008_initial.sql` 为初始基线；更早使用旧 `internal/repo/sqlite` 结构的已发布库不包含当前表结构或该迁移基线。

## 决定

1. **开发与发布双轨生命周期（Dual-track Lifecycles）**：
   - **开发模式（`X.Y.Z-dev`）**：以 `schema.sql` 直接描述最终库表结构。开发期遇到结构变动可自由修改 `schema.sql`，通过重建脚本（`task db:rebuild:dev`）重置本地数据库，不做自动修复。开发库只为开发者服务，不为开发期的中间结构设计数据迁移或双结构兼容；同一结构变动交付给用户时，由发布轨的追加迁移承担。
   - **发布模式**：完全由嵌入式 `goose` 迁移脚本（`internal/adapters/sqlite/migrations/`）管理。`00008_initial.sql` 已冻结，其文件名、编号与内容均不可再修改；后续所有结构变更一律按 `goose` 迁移流程从编号 9 起顺序追加（只追加 `-- +goose Up` 迁移），并为已有发布库提供升级路径与必要的数据修复。已随正式发布交付的迁移文件保持不可变，未发布的追加迁移在交付前可按需合并或调整。
2. **两类数据库互不转化与拒绝跨代升级**：
   - 数据库文件显式标记自身模式，开发库与发布库禁止互相覆盖转换。
   - 发现数据库迁移版本高于当前程序支持的最大版本时，拒绝启动，不把未知结构当作可升级基线。
   - 更早使用旧 `internal/repo/sqlite` 结构的旧发布库不属于本迁移基线，不提供到编号 8 的升级路径。保留旧库供对应旧程序使用，当前程序使用新的数据目录，不把旧库当作空库执行初始建表，也不手工改版本号。
3. **升级前原子备份（VACUUM INTO）与仅向上迁移（Up Only）**：
   - 已有数据的发布库在执行迁移前，通过 SQLite 原生 `VACUUM INTO` 备份当前包含 WAL 在内的完整物理副本。直接复制主数据库文件可能漏掉 WAL 中的提交，因此不用它做恢复基线。备份或迁移失败阻止启动。
   - 升级只走 `Up`，恢复不依赖 `Down`：个别迁移文件可能带有 goose Down 段，但它不是受支持的回退路径。升级故障通过恢复备份并换回旧程序解决；备份不自动清理。

## 放弃的方案

- **全程单一迁移流（每次字段改动均追加 migration）**：在特性分支高频迭代期间会产生大量零碎迁移和合并冲突。
- **由 ORM 自动检查 Diff 并执行动态 DDL**：SQLite 的 ALTER 能力有限，列重命名与类型推断靠猜，容易破坏数据。
- **维护双向 Down 迁移**：对于涉及列删除或数据重组的迁移，Down 脚本往往无法还原已丢失的列数据，给用户带来虚假的安全感。

## 后果

- 开发者必须明确当前运行环境与构建模式；结构变动同时修改 `schema.sql` 并按 `goose` 流程追加发布迁移，验证两轨结构及读写行为一致。旧测试库应使用对应旧程序或新数据目录。
- 详细迁移编写与发布检查规则见 [backend/go/AGENTS.md](../../backend/go/AGENTS.md)。
