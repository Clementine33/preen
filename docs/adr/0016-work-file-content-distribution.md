# 作品文件内容的只读分发：清单与字节

## 1 背景与边界

作品目录（ADR 0011）认识作品、来源元数据与副本绑定，库存认识目录与文件，但二者之间没有桥：详情页要列出「这部作品有哪些图、哪些轨、哪些文本」，就要按作品读出成员目录的文件投影，并按需取这些文件的字节。本决定记录这两件事的形状：**内容清单**（B2）与**文件内容分发**（B3）。

两者都是只读路径，不写入磁盘也不改数据库，因此不占 ADR 0002 §2 的全局准入槽（与 ADR 0015 §3 的缩略图同立场）：读不会破坏「扫描 / 生成 / 执行 / 手动整理」要保护的东西。

## 2 内容清单：`GET /api/v1/works/{rj}/content`

- 清单从**库存**构建，不做现场文件系统遍历：`entries` 行带着 size / mtime / format / bitrate / 宽高 / 时长，是扫描已经裁决过的事实；现场遍历会另立一份真相，与库存分叉。
- 每个副本由 `(library_id, rel_path)` 解析到成员根（ADR 0003 的目录身份），投影成按目录嵌套的树。成员根当前在磁盘上不存在（或不可达）的副本标 `online: false`，树可省略。
- 占位作品（从未出现在磁盘上的关系占位）回答空副本列表，不是 404：它有目录条目，只是没有文件。
- 清单是唯一被接受的内容事实源：详情页的图集、轨道列表、配对与文件浏览器都由它派生，前端不自行猜测目录结构。

## 3 文件内容：只按清单的相对路径分发

- **只服务清单里出现的 rel_path**：请求以作品号与相对路径（或由它们解析出的副本内地址）指名文件，后端把相对路径解析到成员内的绝对路径。**不提供原始路径参数**——清单是白名单，越界段、符号链接逃逸一律拒绝（与 ADR 0002 §1 的成员包含规则同一套检查）。目录不能作为文件读取，打开后还须确认是普通文件。
- 音频带 `Accept-Ranges: bytes`，支持单区间 206：播放器的拖动进度走它。多区间不支持：按整文件 200 回答（HTTP 允许忽略 Range 头；浏览器与 `<audio>` 都只发单区间，不为它们建多区间路径）。
- 图片的 `Content-Type` 由内容判定（jpeg / png / webp），不信任扩展名；字节无法识别为图片时用 `application/octet-stream`。
- 文本（txt / lrc）在**服务端**嗅探字符集（UTF-8 → Shift_JIS → GB18030 候选），在 `Content-Type` 里声明，响应保留原始字节，前端读取 `arrayBuffer()` 后用 `TextDecoder` 按声明的字符集解码。有限样本嗅探区分末尾被截断的多字节字符与非法字节，候选顺序不变。这是 ffprobe 原始标签字节的同一条教训：任何中间层把非法字节改写成 U+FFFD 都是不可逆的破坏；解码必须发生在知道字符集的那一层，且只发生一次。
- **鉴权**：本路由除 `Authorization: Bearer` 外也接受查询参数 `access_token`。查看器的 `<img>` 与播放器的 `<audio>` 按地址加载，带不了请求头，而 `<audio>` 的 Range 拖动只能由元素自己发起。只有完全缺少 Authorization 头时才接受查询令牌；格式错误、空值或错误令牌均拒绝。请求头存在时由它裁决，查询参数救不回错误的头。只此一路如此：其余路由（含 ADR 0015 的缩略图，经 `fetch` 带头取）仍只认请求头——不可变地址里不放令牌，否则令牌变化会让缓存键整体失效。服务端不记录请求地址，令牌不进日志。
- `ETag` 取自 `(size, mtime, content_rev)`，配 `Cache-Control` 让重访不重传。size 与 mtime 相同而内容不同理论上可能（同长度同时刻改写），`content_rev` 兜住扫描可见的变更。原图 URL 可带清单 `thumb_v` 作为可选 `v` 参数，客户端以新地址重新加载同路径图片；文件路由保持 `no-cache`，不因此变成不可变缓存。

## 4 缩略图不在此路

缩略图走 ADR 0015 自己的分层（版本化地址、可丢弃缓存、引擎端口）。文件内容端点只发原图字节；前端的过渡分支（浏览器直接缩放原图）在缩略图服务落地后删除，不留第二条长期路径。

## 5 媒体事实是前置，不是本决定的一部分

宽高与音频时长落在 `entries` 上，由扫描之后的后台补测写入（ADR 0015 §2；ADR 0013 开发期自由改 schema）。清单只投影它们，不现场探测；尚未测得时为 `null`，前端按未知处理。成功补测后的通知与缓存同步见 ADR 0015 §2、§6，更新清单保留当前阅读、配对和播放状态。

## 拒绝的替代方案

- **随扫描同步测量媒体事实（ffprobe，与码率同一探测路径）**：大库首扫被拖长数分钟且无从感知，见 ADR 0015 §2 的否决理由。
- **清单做现场文件系统遍历**：与库存分叉出第二份真相，扫描外的增删改在两个视图里互相矛盾；库存本来就是裁决过的事实源。
- **原始路径参数 + 前缀检查**：把白名单退化成字符串前缀匹配，符号链接与边界 case 都要重新发明 ADR 0002 已经写下的包含规则。
- **客户端字符集探测**：客户端自行猜编码容易产生 mojibake，而且探测逻辑散在每个调用方；服务端一次嗅探一次声明。
- **多区间 206**：没有调用方需要它，实现与测试成本换不来任何真实收益。
- **文件内容缓存进数据库**：字节在磁盘上已经是权威副本，数据库再存一份只多一个同步问题；HTTP 缓存语义（ETag + Cache-Control）已经覆盖重访成本。
- **cookie 鉴权**：要为一条路由引入第二种凭据与其生命周期（签发、过期、跨源 SameSite），而部署是单令牌回环服务。
- **原图走 `fetch` 转 blob、音频走 MediaSource**：原图要整张进内存才能显示；MediaSource 要自己切片、按容器解复用，替浏览器重做 `<audio>` 本来就会的 Range 拖动。
- **把只读分发塞进 ADR 0002 的准入槽**：读不与写竞争任何资源，占槽只会让「扫描时不能看图」这种假忙碌成为规则。
