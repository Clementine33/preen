# 0004 Task 接缝、不透明载荷与工作集共享批次

## 背景

早期的工作集模块与具体的音频转换业务深度耦合，不仅直接定义了音频草稿、规划器与策略载荷，且每种任务类型都需要用户单独选一次文件夹建立独立批次。当引入重命名、元数据刷新等新任务类型时，既容易破坏通用调度契约，又导致用户在不同功能间频繁重复选择相同的目录。

## 决定

1. **清晰的 Task 边界与不透明载荷**：
   - 通用 `workset` 模块只管理批次归属、版本哨兵、计划与草稿的通用存储、会话调度、互斥锁与幂等校验。
   - 具体 Task（如转换、重命名、元数据刷新）作为独立插件包，拥有自己的草稿校验、规范化规则、输入新鲜度检测、规划算法与执行逻辑。
   - 跨越接缝的业务载荷（Payload）以字节切片、类型标记（`kind`）和版本号（`schema_version`）传递；通用调度层读取进度指标及 Task 的可选调度声明，不反序列化或干涉具体业务策略。
   - Task 可实现 `LightPlanner` 声明整个计划生成路径不扫描库存、不探测媒体。声明的 Task 共享一个固定宽度 1 的额外规划 worker；通用 N 个 worker 仍跨 kind 按 FIFO 认领，额外通道提供容量，不划分队列。未声明的 Task 只进通用通道。worker 的认领、取消、Stop 与 drain 均由 workset 统一管理。
   - 未知的载荷 `schema_version` 在每个入口都被拒绝，不尝试兼容读取：计划载荷是冻结事实，宁可拒绝也不猜测。
2. **工作集共享目录批次**：
   - 每个媒体库在同一时刻只有一个活跃的共享批次。用户在界面上选定一组目录后，所有已注册的 Task 均共享这批成员目录。
   - 允许没有音频文件的作品目录进入共享批次，以便执行纯目录重命名或元数据刷新任务。
3. **独立持有计划与草稿**：
   - 各 Task 在共享批次内独立持有自己的草稿参数、版本号、生效计划与执行历史。一种任务的规划或生成不覆盖另一种任务的已有状态。
   - 替换整个批次时原子清空所有 Task 的成员配置与旧计划；任一 Task 存在活跃执行会话时拒绝替换批次。

## 放弃的方案

- **通用层理解全部 Task 业务字段**：导致通用调度层随每个业务特性的变动而频繁重构，破坏单一职责。
- **插件注册表或动态加载**：注册发生在组合根（`internal/app`）的一行里，不需要框架。
- **宽松读取未知 schema 版本**：猜测冻结载荷的含义比拒绝更危险。
- **每种 Task 拥有完全隔离的独立批次**：用户在工作台选择 50 个文件夹后，若想先改名再转换，必须重复选择两次，操作割裂且容易产生选择漂移。
- **仅提高 `generation_concurrency`**：可让轻量任务更早开始，但等待扫描槽的转换仍占 worker，事实缺失时还会叠加媒体探测，未解决不同负载相互阻塞的机制。
- **等待扫描槽时释放 worker**：需要将转换扫描槽上提到 dispatcher，重写 Stop、drain 和 active 记账；扫描本已串行，多转换的吞吐收益不足以支持这项复杂度。

## 后果

- 新增任务类型实现 Task 接口并在装配层注册，按需实现可选调度声明；通用调度器不判断具体 kind，也不从输入刷新为空推断任务轻量。
- 详细调度信封、载荷版本与接口格式见 [worksets.md](../api/worksets.md) 与 [tasks.md](../api/tasks.md)。
