# 0001 媒体库即工作台、处理记录、规划回放、数据库自清理与留存

## 背景

早期设计要求先创建命名的工作集，再在此基础上浏览文件、配置转换任务，并永久保留所有 revision 历史。这种方式给日常整理增加了额外概念层，同时历史载荷长期堆积。而在运行时，常驻进程会源源不断产生扫描、规划和执行会话；SQLite 在删除旧数据行后也不会自动归还文件系统空间。

## 决定

1. **媒体库即工作台**：以媒体库直接承载文件浏览与整理。用户在选定目录范围后生成轻量处理记录，不再要求先建立独立的命名集合，也不再让每个 Task 各建一批；处理记录仍可改名。
2. **只保留当前计划**：每个操作在数据库中只保留当前草稿、当前成功计划及其最新执行结果。保存、生成、执行是独立发起的三阶段动作。旧计划在新计划生成成功后原子替换；生成失败则保留旧成功计划。
3. **计划单次执行与不可变快照**：计划内包含冻结的输入事实快照。一份计划最多执行一次（失败、取消或部分执行均消耗该次机会），再次执行必须重新规划。执行前必须校验快照新鲜度与版本哨兵。
4. **启动收尾与会话自清理**：
   - 进程启动时，在调度器开放前先将残留的非终态会话收尾为 `interrupted`，解除准入占用，保留诊断窗口。
   - 留存窗口从终态时间起算。后台工作协程分批删除过期的终态会话行。
   - 分批清理复用全局准入机制，忙时主动让步；数据库创建时开启增量 auto-vacuum，在清理批次后增量归还空闲页，以 PASSIVE checkpoint 收尾：checkpoint 不等待读者；归还空闲页需要写锁，但只在维护槽内进行。
5. **级联清理与换根约束**：计划以外键归属处理记录，执行以外键归属计划；成功替换计划或删除处理记录时，旧执行及其封面投递需求级联删除。删除媒体库时，在同一事务内删除其名下处理记录；磁盘上的实际音频、已发布封面与回收站文件保留。存在处理记录时禁止修改媒体库根路径，避免相对路径映射错乱。
6. **规划请求回放**：有效幂等键先于当前计划复用、版本条件及活动会话检查，始终指向原规划会话；相同内容回放该会话，不同内容报冲突。失败、取消及中断会话释放键。已完成会话自终态起至少保留 30 天，期间即使原计划被新计划替换，其键仍可回放原会话，但不会恢复旧计划。
7. **活动规划唯一性**：数据库约束同一处理记录的同一操作最多一条 queued/running 规划会话，覆盖两个请求同时通过应用层活动检查的竞态。同键同内容回放原会话，同键不同内容报幂等冲突，不同键报活动会话冲突；不同记录和不同操作不互相占用名额。终态会话释放活动名额。

## 放弃的方案

- **独立命名工作集与永久 revision 历史**：增加数据管理负担与界面心智成本；用户真正需要审阅和追溯的只是当前生效方案与上一轮执行结果。
- **全量 VACUUM 或定时 cron 任务**：全量 VACUUM 需要两倍临时磁盘空间且全程持独占锁，容易造成界面超时；外部 cron 增加了部署依赖。
- **仅在应用退出或启动时集中清理**：常驻后台服务的会话积累无法在运行期得到释放，启动时全量扫描还会显著拖慢就绪时间。

## 后果

- 系统放弃了任意历史计划的时光回溯能力，每次变更都以当前计划为准。
- 数据库自动维护采用轻量增量模式，不承诺文件大小上限（仍取决于未清理的大批量库存与执行日志）。
- 外部契约与数据模型见 [worksets.md](../api/worksets.md) 与 [executions.md](../api/executions.md)。
