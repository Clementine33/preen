# 0001 媒体库即工作台、处理记录、规划回放、数据库自清理与留存

实施状态：2026-10-23 已实现三类历史记录、作品、关系报告及共享来源实体的手动清理 API，以及进程所有的分批 worker、最近摘要、停止／恢复与跨批次准入；网页入口待实现。现有自动留存与空间维护继续有效。

## 背景

早期设计要求先创建命名的工作集，再在此基础上浏览文件、配置转换任务，并永久保留所有 revision 历史。这种方式给日常整理增加了额外概念层，同时历史载荷长期堆积。而在运行时，常驻进程会源源不断产生扫描、规划和执行会话；SQLite 在删除旧数据行后也不会自动归还文件系统空间。

## 决定

1. **媒体库即工作台**：以媒体库直接承载文件浏览与整理。用户在选定目录范围后生成轻量处理记录，不再要求先建立独立的命名集合，也不再让每个 Task 各建一批；处理记录仍可改名。
2. **只公开当前计划，分块暂存后原子提升**：每个操作只公开当前草稿、当前成功计划及其最新执行结果。保存、生成、执行是独立发起的三阶段动作。新计划以 `staging` 状态按表分块写入，每块都是短事务，任何读取和执行入口都看不到暂存内容。每块及最终提升都复核所属生成仍为 running、未提交取消且计划仍为 staging；取消提交后不再接受分块或提升。写完后的一个小事务将新计划置为 ready、建立 revision、提升当前指针、完成生成，并把旧计划退役。生成失败、取消或中断保留旧成功计划；其执行资格仍遵守活动规划互斥、单次执行与新鲜度规则。暂存属于生成会话，失败残留交给分批清理，不形成用户可见子批次。
3. **计划单次执行与不可变快照**：计划内包含冻结的输入事实快照。一份计划最多执行一次（失败、取消或部分执行均消耗该次机会），再次执行必须重新规划。执行前必须校验快照新鲜度与版本哨兵。
4. **启动收尾与会话自清理**：
   - 进程启动时，在调度器开放前先将残留的非终态会话收尾为 `interrupted`，解除准入占用，保留诊断窗口。
   - 留存窗口从终态时间起算。后台工作协程分批删除过期的终态会话行。扫描当前保留 7 天，规划当前保留 30 天，这是删除资格，不是运行频率。
   - 自动维护只处理过期扫描／规划记录、无投递引用的 done 下载及空间维护。服务开放前尝试一轮；现有后台循环首次等 15 分钟，随后完成一轮等 24 小时，忙、未完成或预算耗尽等 15 分钟重试。手动运行不重置此时钟；双方共用资格与准入，不另设定时清理器。
   - 分批清理复用全局准入机制，忙时主动让步；数据库创建时开启增量 auto-vacuum，在清理批次后增量归还空闲页，以 PASSIVE checkpoint 收尾：checkpoint 不等待读者；归还空闲页需要写锁，但只在维护槽内进行。
5. **退役、分批清理与换根约束**：计划以外键归属处理记录，执行以外键归属计划。成功替换计划时，旧计划及其执行立即不可读、不可执行；替换处理记录时，在同一事务内退役旧记录、释放每库唯一的当前记录名额并写入新成员及草稿，保留版本、活动会话与幂等守卫。退役不同于 orphaned，任何读取和清理预览都不公开退役数据。删除媒体库也在删除事务内退役其处理记录，不留下可审阅孤立记录；解除副本绑定、删除全库库存及媒体库行仍同步完成，其成本取决于整库规模，不承诺工作集短事务预算。磁盘上的实际音频、已发布封面与回收站文件保留；存在当前处理记录时禁止修改媒体库根路径，避免相对路径映射错乱。
   - 计划或记录退役时，在同一事务内取消 pending/running 封面投递。退役写入先取得封面发布互斥，再开启数据库事务，提交后释放互斥并停止无需求下载；文件发布持同一互斥复核资格，因此发布要么先于退役提交完成，要么不发生，不在持有数据库写锁时等待发布锁。
   - 一个进程所有的退役清理任务按叶到根、每批至多 1000 行且只删一张表，父行仅在子表清空后删除，批间释放写锁。它处理退役计划、退役记录及终态生成遗留的 staging；每次删除在事务内复核资格，不能删除正在生成的暂存。启动时先中断残留生成再清理、调度器随后开放；退役和生成终态唤醒清理，现有维护周期也尝试清理。此任务只处理不可见数据，不占文件管理准入槽，也不复用决定 8 的用户可见手动清理流程。
6. **规划请求回放**：有效幂等键先于当前计划复用、版本条件及活动会话检查，始终指向原规划会话；相同内容回放该会话，不同内容报冲突。失败、取消及中断会话释放键。已完成会话自终态起至少保留 30 天，期间即使原计划被新计划替换，其键仍可回放原会话，但不会恢复旧计划。
7. **活动规划唯一性**：数据库约束同一处理记录的同一操作最多一条 queued/running 规划会话，覆盖两个请求同时通过应用层活动检查的竞态。同键同内容回放原会话，同键不同内容报幂等冲突，不同键报活动会话冲突；不同记录和不同操作不互相占用名额。终态会话释放活动名额。
8. **部署级手动记录清理**：
   - 设置页先检查、按类别确认，再后台分批执行；删除时在事务内重新校验资格，预览不锁定记录。扫描终态记录当前保留 7 天，已结束规划会话当前保留 30 天；手动与自动清理共用 app 注入的留存参数及事务删除函数，规划窗口继续与幂等保证对齐，不另写一份常量；无投递引用的已完成下载、无副本且无个人资料的作品、无用途关系报告及无引用来源实体不另设等待期。
   - 清理只删除记录，不操作媒体、封面、缩略图或回收目录文件，不新增收缩按钮；空间归还沿用增量维护。自动维护不扩展为自动清理作品或关系报告。
   - 全局仅一轮手动清理，忙时拒绝且不排队。运行不依附 HTTP 请求或页面；每批释放维护槽让步，重新申请遇普通活动则中断。gate 在同一锁内维护跨批次的手动运行标记，阻止第二轮清理及自动维护抢槽；标记不阻止普通任务在让步间隙开始。停止、失败或中断保留已提交批次，重启不自动续跑。
   - 执行顺序为历史会话与已完成下载、作品、关系报告、共享来源实体；各作品目录类别的保护条件与依赖闭包规则由作品目录模块定义，手动清理复用其事务校验与批次边界（报告批次目标 500，不拆分强连通组；停止可能等待当前大组释放写锁）。
   - 仅保存当前／最近运行摘要，删除计数与删除同事务提交；下一轮替换摘要，不建立永久清理流水。维护准入不能代替事务内的用户资料和引用保护。

9. **计划摘要与成员结论生成时落库**：当前计划的计数与摘要原因，以及每个记录成员除 Member Input 外的结论（含排除、无规划输入与零组件成员），只由冻结计划决定；业务层在暂存前用完整的内存快照计算一次，计数随计划行写入，成员结论作为独立序列分块写入计划的子表。暂存事务只持久化，提升仍只改元数据；摘要与成员列表读取不再解码组件载荷，Member Input 仍在读取时计算，成员审阅复用保存的冻结部分并读取该成员自己的组件。

## 放弃的方案

- **独立命名工作集与永久 revision 历史**：增加数据管理负担与界面心智成本；用户真正需要审阅和追溯的只是当前生效方案与上一轮执行结果。
- **整份计划单事务写入与替换时级联删除**：持锁时间随成员、音频与旧执行载荷增长；分块暂存、原子提升与退役清理在保留替换语义的同时缩短每次占用写锁的时间。
- **每次读取重算计划计数与成员结论、进程内按 planId 缓存**：前者读取成本随组件数增长，后者引入失效与多进程一致性问题；冻结计划不变，生成时算一次落库即可。
- **用户可见子批次**：会引入部分子批次已执行、其余计划已过期等组合状态；持久化分块无需改变用户的一个工作集、一份当前计划模型。
- **每库排队多个 Workset**：推翻每库至多一个当前记录与显式替换语义，额外引入批次排队和选择成本。
- **全量 VACUUM 或定时 cron 任务**：全量 VACUUM 需要两倍临时磁盘空间且全程持独占锁，容易造成界面超时；外部 cron 增加了部署依赖。
- **仅在应用退出或启动时集中清理**：常驻后台服务的会话积累无法在运行期得到释放，启动时全量扫描还会显著拖慢就绪时间。
- **把预览当作删除授权快照，或让清理全程占用维护槽**：前者可能错删预览后新增个人资料的作品，后者会长时间阻止日常任务；短事务内复核与批次间让步分别处理这两个问题。

## 后果

- 系统放弃了任意历史计划的时光回溯能力，每次变更都以当前计划为准。
- 数据库自动维护采用轻量增量模式，不承诺文件大小上限（仍取决于未清理的大批量库存与执行日志）。
