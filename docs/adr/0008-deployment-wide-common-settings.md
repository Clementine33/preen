# 0008 部署级公共设置

## 背景

转换的公共设置起初只保存在某一个处理记录的草稿里，「转换全局设置」页读的其实是当前记录的草稿。同一台机器上的两个媒体库因此可以长期持有两套公共设置：用户在第一个库改完，进第二个库看到的仍是旧值，以为修改丢了。策略槽已经否认了草稿里的活引用（[0005](0005-declarative-audio-planning.md)），所以这里需要的是推送语义。

## 决定

1. **部署级单一权威事实（Deployment-wide Common Settings）**：
   - 公共设置按 Task 类型隔离，每类一份部署级载荷；目前只有转换 Task 写入，未接入的 Task 没有这一行。
   - 新建的处理记录以该载荷为种子草稿的起点；没有存过或载荷读不了时，用 Task 自己的种子值。
2. **显式事务性全量推送**：
   - 用户在界面保存部署级公共设置时，后端在单个数据库事务内原子更新全局公共记录，并全量推送到该 Task 类型的所有现存可编辑草稿中。
   - 推送时整体替换各草稿的公共段，成员记录（覆盖、排除以及「没有覆盖」这件事）逐字保留；每条草稿的哈希与 operation 版本随之推进。
3. **严格的全有或全无守卫（All-or-Nothing）**：
   - 候选集合与每条候选的会话状态在事务内重新读取：任一待同步记录正在生成或执行，或其草稿缺失、损坏、schema 版本未知，整次保存以冲突拒绝。跳过它正是这条规则要消灭的部分更新。孤立记录（库已不存在）只读，不参与同步。
4. **冻结计划免疫**：
   - 公共设置的保存与推送仅作用于未执行的草稿，不改写已经生成的冻结计划。草稿哈希变动后，既有的计划新鲜度校验机制自然识别并提示用户重新生成。

## 放弃的方案

- **逐记录异步后台补偿同步**：会暴露漫长的中间不一致状态，且后台静默重试机制复杂。
- **运行时动态合成全局值（不物理写进草稿）**：导致草稿与其生成的计划无法形成确定性快照，草稿哈希校验随之失效。
- **由界面在前端并发发起多个媒体库的更新请求**：网络抖动或部分失败会留下难以排查的脏配置。

## 后果

- 同类记录中任一条正在生成或执行时，公共设置无法保存，需等该会话结束。
- 详细 API 参数及错误码参见 [conversion.md](../api/conversion.md) 与 [worksets.md](../api/worksets.md)。
