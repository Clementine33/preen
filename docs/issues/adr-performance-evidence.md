## 1. 音频编码调度与并发收益

- **关联决策**：[ADR 0006](../adr/0006-execution-sessions-and-component-results.md)（执行会话与组件结果）
- **实验日期**：2026-09-22（原 0007）

### 背景与负载
执行会话为全局单实例运行。会话内部按冻结单元推进：生成全部输出、校验、提交，然后清理过时音频。由于转码调用单线程 ffmpeg，串行执行会导致多核闲置，单个耗时较长的大文件也会阻塞后续目录。

**测试负载**：2.67 GiB WAV 文件集（包含单个组件 6 个音频文件，目标转码为 MP3 320 kbps）。

| 调度策略 | 桌面环境（耗时 / 核心利用） | NAS 环境（耗时 / 核心利用） | 相对收益 |
|---|---|---|---|
| 单线程串行 | 100.8 s（1.10 核） | 149.1 s（1.14 核） | 基准（1.00x） |
| 2 个编码 worker | 53.5 s（1.88x） | 83.1 s（1.79x） | 耗时下降约 44%–47% |
| 4 个编码 worker | 46.0 s（2.19x） | 59.6 s（2.50x） | 耗时下降约 54%–60% |
| SSD staging | 129.0 s（0.78x） | 未运行 | 跨设备复制增加额外耗时 |

### 测量观察
- 两种环境下磁盘 I/O 占用均低于 9%。采用 4 worker 并发时，单文件编码耗时膨胀 15%–25%，批次总耗时取决于体积最大的单个文件（单文件编码无法再拆分）。
- 会话报告写入方面：1000 组件全量重写单次耗时 4.98 s，产生 420 MB WAL 日志；改为逐组件追加后单次耗时 0.19 s，产生 13 MB WAL，因此选用逐组件持久化策略。

## 2. 轻量任务规划耗时

- **关联决策**：[ADR 0012](../adr/0012-metadata-refresh-and-directory-rename-planning.md)（元数据刷新与目录改名规划）
- **实验日期**：2026-10-05（原 0014）

在 NAS 环境下，选取 5 个作品目录与相同初始库存的独立 SQLite 副本，各运行 5 次生成测试（关闭计划复用，仅读原媒体）：
- **Rename 计划生成**：中位数由 92.928 ms 降至 3.837 ms。
- **Metadata 计划生成**：中位数由 55.960 ms 降至 3.822 ms。

该测量包含异步调度与持久化耗时，仅反映热缓存条件下的计算表现，不构成整库冷扫描的耗时指标。

## 3. 媒体事实分析与探测策略

- **关联决策**：[ADR 0013](../adr/0013-derived-media-thumbnails-content-and-facts.md)（衍生媒体事实与内容交付）
- **实验日期**：2026-09-30（原 0015）

图片尺寸与音频时长随条目记录于 `entries` 表，使前端能够在图片像素加载完成前计算标本框与胶片带排版。

### 调度与 I/O 隔离
- **解耦扫描流程**：全库扫描与成员刷新完成后，由独立后台任务按游标扫描未知条目。
- **可抢占让步机制**：后台任务持有可被抢占的执行槽。当系统出现扫描、文件操作或转码请求时，后台探测即刻退出并保存当前写入批次（每 64 个文件或在退出时写回一次），让出 I/O 资源。
- **通知机制**：事实写入后发送 `changed` SSE 事件；客户端连接时拉取最新状态，后续合并事件信号，不引入全量事件日志存储。

### 探测吞吐与并发验证（SMB 机械盘无缓存场景）
- **原生文件头解析**：
  - 图片使用标准库 `image.DecodeConfig`。
  - WAV 读取 `fmt`/`data` 块计算时长。
  - MP3 读取首帧 Xing/Info/VBRI 标记，无标记时按固定码率估算。
  - M4A（MP4 容器）定位 `moov` 盒子读取 `mvhd` 时长与刻度，略过逐帧索引（比对 ffmpeg 与 qaac 生成的 547 个样本，与 ffprobe 差值在 1 ms 以内）。
  - 未采用音轨级 `mdhd`（包含预填充采样造成的约 21 ms 偏差）或 `elst` 列表。
- **并发实测表现**：
  - 原生解析 1 并发：约 26 条目/s。
  - **原生解析 8 并发**：**约 45 条目/s**（并发掩盖部分网络往返延迟，同时避免耗尽机械盘 I/O 队列）。
  - 原生解析 16/32 并发：50~58 条目/s（单请求排队时间成倍增长，吞吐边际收益放缓）。
  - ffprobe 外部进程（8 并发）：约 18 条目/s。在 32 并发全量调用 ffprobe 时，p95 延迟升至约 5 s。

## 4. 库存扫描与 SQLite 合并吞吐

- **关联决策**：[ADR 0002](../adr/0002-direct-file-management-and-admission.md)（文件管理与准入）、[ADR 0010](../adr/0010-defer-single-writer.md)（数据库单写者模型）
- **实验日期**：2026-10-04（原 0017）

### 原始实现与改动项对照

| 维度 | 原始实现 (commit `b899386f`) | 改动后实现 |
|---|---|---|
| **扫描调度** | 每个目录均为独立任务，作品内部并发下探 | 顶层分类发现 + 作品级任务，作品内部顺序遍历 |
| **工作队列** | 默认 4 个目录 worker；通道有界但未限制调度切片 | 默认 32 个作品 worker；队列容量固定为 `2 × workers` |
| **作品边界与绑定** | 仅按仓库直接子目录名称匹配，深层作品不绑定 | 持久化 `is_work_root`，支持任意深度作品根绑定 |
| **未修改条目写入** | staging 全部执行 upsert，更新 `scan_id`、`updated_at` | 先增条件更新，后提前至 SELECT 过滤；未变动行不触发写操作 |
| **staging 索引** | 建立主键、session、status 3 个索引 | 移除冗余索引，仅保留 `(session_id, path)` 主键 |
| **绑定关系写入** | 每个副本独立执行两次 Exec | 事务内复用两条 Prepare 语句，仅写新增或有变动的 work_id |
| **失效绑定清理** | 展开为 SQL `IN (...)` 参数，超过 32,765 根触发错误 | 采用事务临时集合 + 分批写入，清理语句仅绑定 `library_id` |

### 扫描并发度实测（空库，冷完整流程）

| 配置 | 冷流程总耗时 |
|---|---:|
| 16 worker + 目录排序 | 7.627970 s |
| 32 worker + 目录排序 | 6.717681 s |
| 32 worker + 保持目录原生返回顺序 | 6.677796 s |

实测中，保留目录原生顺序相比显式排序的耗时差异为 0.6%，且未体现出稳定的磁盘顺序相关性，因此保留 **32 worker + 排序** 的确定性方案。

### SQL 合并基准测量（Benchstat 中位数）
测试样本：NAS 28,839 项条目（5,760 目录，23,079 文件，940 作品根/副本），NVMe 挂载卷环境，`-benchtime=1s`，仅度量 `MergeStaging`：

| 评估项目 / 场景状态 | 基线 (ms/op) | 候选 (ms/op) | 耗时变化 | 统计显著性 (p) |
|---|---:|---:|---:|---:|
| **移除 staging 冗余索引**（热扫均值） | 673.350 | 594.801 | -11.67% | — |
| **SELECT 提前过滤**（空库） | 369.781 | 371.349 | +0.42% | 0.247（无显著回退） |
| **SELECT 提前过滤**（条目未变动重扫） | 283.799 | 179.442 | -36.77% | < 0.001（显著减少耗时） |
| **绑定写入过滤 + Prepare 复用**（空库） | 369.379 | 347.990 | -5.79% | < 0.001（显著减少耗时） |
| **绑定写入过滤 + Prepare 复用**（重扫） | 178.462 | 155.239 | -13.01% | < 0.001（显著减少耗时） |

### 规模边界验证与 Pragma 测试
- **参数数量上限**：使用 32,767 个作品根进行合并测试，原实现触发 `too many SQL variables` 报错；改用临时表批量写入后执行正常。在 940 根的标准测试中，空库合并中位数为 350.67 → 349.47 ms (p=0.853)，热扫为 155.78 → 155.75 ms (p=0.796)，未引起性能回退。
- **SQLite 事务 Pragma**：在 ext4 卷上对比 `synchronous=FULL`（587.36 ms）与 `NORMAL`（598.33 ms），未观察到写入提速；系统保留 `synchronous=FULL`、`cache_size=-2000`、`wal_autocheckpoint=1000` 设置。
- **未采纳的方案**：放弃“仅在 staging 记录变更行”的方案，因其会导致无法判定已被物理删除的过期项；不引入 ORM、路径字典或层级闭包表。

## 6. 输出校验与故障实验

- **关联决策**：[ADR 0006](../adr/0006-execution-sessions-and-component-results.md)（执行会话与组件结果）
- **实验日期**：2026-10-04（原 0019）

### Opus 原生 Ogg CRC32 校验收益
测试样本：320 秒 WAV 音频转码为 Opus 128 kbps（4 workers，4 组件）：
- **基线**：ffmpeg 完整解码并计算 SHA。
- **候选**：Go 实现单逻辑流 Ogg 页面级 CRC32 校验（检查 BOS、serial、连续性及 EOS，EOS 后禁止出现额外字节），并在同一数据流中计算 SHA。

| 交替测试组 | 基线总执行时间 | Go Ogg CRC32 校验时间 |
|---|---:|---:|
| 1 | 2.986812 s | 2.304068 s |
| 2 | 2.905738 s | 2.329436 s |
| 3 | 2.955712 s | 2.292407 s |
| 4 | 3.062531 s | 2.264683 s |
| 5 | 2.984409 s | 2.352212 s |

执行中位数由 2.984409 s 变为 2.304068 s（下降 22.80%），5 组测试均降低了耗时，采用 Ogg 页面级流式校验。

### 校验边界与接受的剩余风险
- **解码通过不代表音频无截断**：在 FFmpeg 9.0.1 故障注入实验中，MP3 音频在帧边界处截断仍能以状态码 0 正常退出且 stderr 无输出；M4A 在末尾截去 8 字节后仍能通过探针与解码检查。这表明常规解码无法作为判定数据无丢失的唯一证据。
- **自建解析器的兼容性代价**：对 4 个 NAS 库（4,686 个 MP3，1,547 个 M4A）进行格式扫描，严格的格式规则误拒了 2,205 个可正常播放的文件（其中包括合法的 LAME 3.99r 标签文件），表明维持格式 AST 解析器的兼容成本过高。
- **权衡与策略**：MP3/M4A 维持原有的输出探针与标准完整解码校验，并在写出后调用文件系统 `Sync()` 与 `Close()`，发布前核对文件体积。系统明确接受以下剩余风险：底层存储在接口返回成功时发生的数据损坏，以及外部进程在不改变文件体积前提下的原地修改；不为 MP3/M4A 引入专有 AST 格式解析器。
